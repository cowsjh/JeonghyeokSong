## 1. 상속 입문

### is-a 관계

상속은 두 객체 사이의 **"~은 ~이다(is-a)"** 관계를 모델링한다.

> "상속은 다른 객체의 속성과 행동을 그대로 물려받아 새 객체를 만든 다음, 그것을 확장하거나 특수화하는 것이다."

사과와 바나나는 *과일이다* — 그래서 과일의 속성(이름, 색, 크기)과 행동(익는 과정)을 물려받는다. 이 관계는 항상 **일반적인 것 → 구체적인 것** 방향으로 흐른다: 정사각형은 직사각형이고, 직사각형은 사각형이고, 사각형은 도형이다.

### 왜 쓰는가

C++에서 복잡한 클래스를 만드는 두 가지 큰 접근법 중 하나가 상속이다(다른 하나는 컴포지션 — "has-a" 관계). 상속은 파생 클래스가 이미 검증된 기반 클래스의 특성을 그대로 물려받고, 거기에 특수한 기능만 추가하게 해줘서 **코드 재사용**을 가능하게 한다.

### 컴포지션과의 차이

| 관계 | 예 | 의미 |
|---|---|---|
| 상속(is-a) | `Car`는 `Vehicle`이다 | 파생 객체가 곧 기반 객체의 한 종류 |
| 컴포지션(has-a) | `Car`는 `Engine`을 가진다 | 별개의 객체를 조합해서 담고 있음 |

두 관계를 혼동하면 잘못된 설계(예: "로봇 팔은 조인트를 가진다"인데 "로봇 팔은 조인트다"로 상속시키는 것)로 이어지기 쉽다.

> ROS2에서 `class MyNode : public rclcpp::Node`는 정확히 is-a 관계다 — "내 노드는 (rclcpp가 정의한) Node의 한 종류다"라는 선언이고, 그래서 `rclcpp::Node`가 제공하는 `create_publisher`, `get_logger` 등을 내 클래스에서 그대로 쓸 수 있다.

## 2. C++에서의 기본 상속

### 문법

```cpp
class BaseballPlayer : public Person
{
    // ...
};
```

`: public BaseClass`가 상속을 선언한다. 여기서 `public`은 [5절](#5-상속과-접근-지정자)에서 다룰 "상속 종류"를 의미한다.

### 무엇이 상속되는가

파생 클래스는 기반 클래스의 **멤버 변수와 멤버 함수를 모두** 물려받는다.

```cpp
class Person
{
public:
    std::string m_name{};
    int m_age{};
    const std::string& getName() const { return m_name; }
    int getAge() const { return m_age; }
};

class BaseballPlayer : public Person
{
public:
    double m_battingAverage{};
    int m_homeRuns{};
    // getName(), getAge(), m_name, m_age는 물려받았으므로 다시 안 써도 됨
};
```

### 무엇이 상속되지 않는가

- **생성자는 자동으로 상속되지 않는다.** 아래 코드처럼 파생 클래스 생성자가 자기 멤버만 초기화하면, 기반 클래스 생성자가 호출되지 않아 상속받은 멤버가 초기화되지 않은 채로 남을 수 있다.

```cpp
BaseballPlayer(double battingAverage = 0.0, int homeRuns = 0)
    : m_battingAverage{ battingAverage }, m_homeRuns{ homeRuns }
{
    // m_name, m_age는 여기서 초기화되지 않음 — 문제!
}
```

올바른 해결법은 [4절](#4-파생-클래스의-생성자와-초기화)에서 다룬다.

- **private 멤버는 파생 클래스에서 접근할 수 없다** — 자세한 접근 규칙은 [5절](#5-상속과-접근-지정자)에서 다룬다.

### 상속 체인

`Supervisor`가 `Employee`를 상속하고, `Employee`가 `Person`을 상속하는 식으로 여러 단계를 이어 붙일 수 있다 — 단계가 늘수록 점점 더 구체화되면서도 이전 단계의 재사용성은 유지된다.

## 3. 파생 클래스의 생성 순서

### 왜 기반 클래스가 먼저 생성되는가

> "자식은 부모 없이 존재할 수 없다."

파생 클래스 객체는 개념적으로 **기반 부분 + 파생 부분** 두 조각으로 이루어져 있다. 파생 부분이 기반 부분의 멤버를 쓸 수도 있으므로, 기반 부분이 먼저 완전히 초기화되어 있어야 안전하다 — 그래서 C++은 상속 트리를 **최상위 기반 클래스부터 아래로** 순서대로 생성한다.

### 다단계 상속에서의 체인

`D`가 `C`를, `C`가 `B`를, `B`가 `A`를 상속한다면, `D`를 생성할 때 순서는 **A → B → C → D**다.

```cpp
// 출력 예시
생성 A:
A
생성 B:
A
B
생성 C:
A
B
C
생성 D:
A
B
C
D
```

각 줄은 그 시점까지 생성자가 실행된 클래스들을 보여준다 — 매번 기반 클래스들의 생성자가 먼저 다시 실행되고, 그 위에 다음 단계 생성자가 실행되는 구조다.

> 소멸 순서는 이 반대(LIFO)라는 점을 [Ch.15 소멸자](../chapter15MoreOnClasses/main.md)에서 배운 원칙과 그대로 연결해서 기억하면 된다 — 나중에 생성된 것을 먼저 정리해야 안전하다는 논리가 상속 체인에도 동일하게 적용된다.

## 4. 파생 클래스의 생성자와 초기화

### 기반 클래스 생성자를 명시적으로 호출하기

파생 클래스의 멤버 초기화 목록에서 기반 클래스 생성자를 직접 호출해서, 어떤 생성자로 기반 부분을 초기화할지 지정한다.

```cpp
class Derived : public Base
{
public:
    double m_cost{};

    Derived(double cost = 0.0, int id = 0)
        : Base{ id }      // 기반 클래스 생성자를 명시적으로 호출
        , m_cost{ cost }
    {
    }
};
```

### 왜 상속받은 멤버를 직접 초기화할 수 없는가

> "C++은 클래스가 생성자의 멤버 초기화 목록에서 상속받은 멤버 변수를 초기화하는 것을 막는다."

이 제약이 존재하는 이유는 **const와 참조 멤버를 보호**하기 위해서다. 만약 파생 클래스가 상속받은 멤버를 마음대로 재초기화할 수 있다면, 정확히 한 번만 설정되어야 하는 const 값이 파생 클래스에서 다시 설정되며 그 계약이 깨질 수 있다. 그래서 **기반 부분의 초기화는 반드시 기반 클래스 생성자를 통해서만** 이뤄지도록 강제한다.

```cpp
Derived derived{ 1.3, 5 };
// Base(5)가 먼저 호출되어 m_id를 초기화
// 그다음 m_cost가 1.3으로 초기화됨
```

> [!NOTE]
> **위치는 상관없다**
> "Derived 생성자의 멤버 초기화 목록에서 Base 생성자를 어디에 적든 상관없다 — 항상 가장 먼저 실행된다." [3절](#3-파생-클래스의-생성-순서)에서 본 생성 순서 규칙이 이 지점에서 문법적으로 강제되는 셈이다.

다단계 상속에서는 각 클래스가 **자신의 바로 위 부모**의 생성자만 호출하면 되고, 그 연쇄가 자동으로 최상위까지 이어진다.

## 5. 상속과 접근 지정자

### 세 가지 멤버 접근 지정자

| 접근 지정자 | 누가 접근 가능한가 |
|---|---|
| public | 누구나 |
| protected | 그 클래스 자신 + friend + **파생 클래스** |
| private | 그 클래스 자신 + friend만 (파생 클래스는 접근 불가) |

protected는 public과 private의 중간 지점으로, "바깥에는 숨기지만 자식에게는 열어준다"는 절충안이다.

### protected를 둘러싼 논쟁 — 왜 private을 우선하라고 하는가

protected 멤버를 노출하면, 그 멤버의 구현이나 의미가 바뀔 때마다 **그걸 상속한 모든 파생 클래스**를 함께 고쳐야 한다. 파생 클래스가 하나둘일 때는 괜찮아도, 계층이 커질수록 이 결합도가 유지보수 부담으로 커진다.

> "파생 클래스가 계획되어 있고, private 멤버에 접근하는 인터페이스를 구축·유지하는 비용이 너무 클 때만 protected를 써라."

기본 원칙은 여전히 "private을 protected보다 우선하라"다.

### 상속 종류에 따른 변환

상속 자체에도 세 종류가 있고, 각각 상속받은 멤버의 접근 수준을 다르게 바꾼다.

| 기반 클래스에서의 접근 | public 상속 | private 상속 | protected 상속 |
|---|---|---|---|
| public | public | private | protected |
| protected | protected | private | protected |
| private | 접근 불가 | 접근 불가 | 접근 불가 |

- **public 상속**(가장 흔함): public은 public, protected는 protected 그대로 유지.
- **protected 상속**(드묾): public과 protected 멤버가 모두 protected로 격하됨.
- **private 상속**(드묾): "기반 클래스의 모든 멤버가 private으로 상속된다" — 파생 클래스 밖에서는 기반 클래스 기능에 전혀 접근할 수 없게 된다.

### 권장 사항

> "특별한 이유가 없다면 public 상속을 써라." "protected 멤버보다 private 멤버를 우선하라."

## 6. 파생 클래스에 새 기능 추가하기

### 핵심 개념

> "기반 클래스 기능을 물려받은 다음, 새 기능을 추가하거나, 기존 기능을 수정하거나, 원치 않는 기능을 숨길 수 있다."

가장 단순한 확장은 파생 클래스에 그냥 새 멤버 함수/변수를 선언하는 것이다.

```cpp
class Derived : public Base
{
public:
    int getValue() const { return m_value; }  // Base에는 없던 새 함수
};
```

파생 클래스는 기반 클래스의 protected 멤버에도 접근할 수 있으므로, 새 함수가 상속받은 데이터를 활용해서 동작할 수 있다.

### 기반 클래스를 직접 고치지 않고 파생 클래스에 추가하는 이유

- **서드파티 라이브러리** — 구매하거나 외부에서 가져온 코드를 수정하면 업데이트할 때 그 수정이 덮어써질 위험이 있다.
- **표준 라이브러리 클래스** — 직접 수정할 수 없지만, 상속으로 확장은 가능하다.
- **미리 컴파일된 코드** — 헤더만 제공되는 경우, 상속이 유일한 확장 수단이다.

### 방향은 한쪽으로만 흐른다

> "Base 타입의 객체는 Derived의 getValue() 함수에 접근할 수 없다."

파생 클래스는 기반 클래스의 것을 물려받지만, 그 반대(기반 클래스가 파생 클래스의 새 기능을 아는 것)는 불가능하다 — 상속 관계는 항상 파생 → 기반 한 방향으로만 지식이 흐른다.

## 7. 상속받은 함수 호출과 재정의

### 함수 이름 탐색 순서

컴파일러는 **가장 파생된 클래스부터 시작해서 위로 거슬러 올라가며** 이름이 일치하는 함수를 찾는다. 파생 클래스에 같은 이름의 함수가 하나라도 있으면, 그 클래스 레벨에서 탐색을 멈추고 오버로드 후보를 그 안에서만 고른다.

### 기반 함수를 재정의하기

파생 클래스가 기반 클래스와 같은 이름의 함수를 정의하면, 파생 버전이 우선한다. 기반 클래스 객체는 여전히 원래 동작을 유지하면서, 파생 객체만 새 동작을 갖게 된다.

> 접근 지정자는 독립적으로 바뀔 수 있다 — private이던 기반 함수를 파생 클래스에서 public으로 재정의하는 것도 가능하고 그 반대도 가능하다.

### 재정의 안에서 기반 버전을 명시적으로 호출하기

```cpp
void identify() const
{
    std::cout << "Derived::identify()\n";
    Base::identify();  // 범위 지정 연산자로 기반 버전을 명시적으로 호출
}
```

`Base::` 없이 그냥 `identify()`라고 쓰면, 컴파일러는 가장 파생된 버전(자기 자신)을 다시 찾아서 **무한 재귀**에 빠진다 — 재정의 함수가 자기 자신을 호출하는 셈이기 때문이다.

friend 함수(예: `operator<<`)의 기반 버전을 호출할 때는 `static_cast`로 임시로 기반 타입처럼 취급한다.

```cpp
out << static_cast<const Base&>(d);  // Base의 operator<< 호출
```

### 오버로드 세트를 가리는 문제 — using 선언

파생 클래스가 오버로드된 함수 중 **하나만** 재정의하면, 컴파일러는 그 순간부터 기반 클래스의 나머지 오버로드를 전부 무시하고 파생 클래스 안에서만 후보를 찾는다.

```cpp
class Derived : public Base
{
public:
    using Base::print;   // Base의 모든 print() 오버로드를 다시 보이게 함
    void print(double) { /* ... */ }
};
```

`using` 선언으로 기반 클래스의 오버로드 전체를 파생 클래스의 오버로드 후보군에 다시 합류시킬 수 있다.

## 8. 상속받은 기능 숨기기

### 접근 수준 바꾸기 — using 선언

`using` 선언으로 상속받은 멤버의 접근 수준을 바꿀 수 있다. 예를 들어 protected였던 기반 함수를 파생 클래스에서 public으로 노출한다.

```cpp
class Derived : public Base
{
public:
    using Base::printValue;  // 괄호 없이 — 함수 호출이 아니라 이름 자체를 다시 노출
};
```

> [!WARNING]
> **한계**
> private 기반 멤버는 애초에 파생 클래스에서 접근 자체가 안 되므로, 이 방법으로 접근 수준을 높일 수 없다 — **파생 클래스가 이미 접근 가능한 멤버**만 재노출할 수 있다.

### 기능 숨기기

반대로, 상속받은 기능을 파생 클래스에서 private으로 만들어 "파생 클래스를 통해서는 접근할 수 없게" 숨길 수도 있다.

> [!WARNING]
> **진짜 캡슐화는 아니다**
> 접근 제어는 컴파일 타임 검사이지 런타임 보장이 아니므로, 기반 타입으로 캐스팅하면 숨긴 기능도 다시 접근할 수 있다 — "숨김"은 완벽한 차단이 아니라 실수 방지용 장치에 가깝다.

### 상속받은 함수를 delete하기

```cpp
class Derived : public Base
{
public:
    int getValue() const = delete;  // 파생 객체를 통한 호출을 막음
};
```

기반 버전은 여전히 `Base::getValue()`처럼 명시적 스코프로 호출하거나, 기반 클래스 참조로 업캐스트해서 접근할 수 있다.

> [!NOTE]
> **업캐스트 시 참조를 쓸 것**
> 업캐스트할 때 값으로 복사하면 파생 객체의 기반 부분만 잘라서 복사(슬라이싱)하게 되므로, 불필요한 복사를 피하려면 참조를 쓴다.

## 9. 다중 상속

### 문법

```cpp
class Teacher : public Person, public Employee
{
    // Person과 Employee 양쪽을 모두 상속
};
```

콜론 뒤에 기반 클래스를 쉼표로 나열하고, 각각에 접근 지정자를 붙인다.

```cpp
Teacher(std::string_view name, int age, std::string_view employer, double wage, int teachesGrade)
    : Person{ name, age }, Employee{ employer, wage }, m_teachesGrade{ teachesGrade }
{
}
```

생성자는 각 기반 클래스를 개별적으로 초기화한다 — [4절](#4-파생-클래스의-생성자와-초기화)의 규칙이 기반 클래스 개수만큼 반복되는 것뿐이다.

### 다이아몬드 문제

가장 심각한 문제는 **두 기반 클래스가 다시 같은 하나의 클래스를 상속**할 때 발생한다.

```
        PoweredDevice
        /            \
   Scanner          Printer
        \            /
          Copier
```

`Copier`가 `Scanner`와 `Printer` 양쪽을 다중 상속하면, `PoweredDevice`를 **하나만 가져야 하는지 두 개(각 경로에서 하나씩) 가져야 하는지가 모호**해진다. 상속 깊이가 늘수록 이 모호함은 기하급수적으로 복잡해진다.

### 이름 충돌 — 모호한 함수 호출

두 부모가 이름이 같은 함수를 각각 정의하고 있으면 호출이 모호해진다.

```cpp
WirelessAdapter c54G{ 5442, 181742 };
std::cout << c54G.getID();  // 에러: 어느 부모의 getID()인지 불명확
```

해결하려면 명시적으로 스코프를 지정해야 한다: `c54G.USBDevice::getID()`.

### 정당한 사용 사례 — 믹스인(mixin)

**믹스인**은 "다른 클래스에 속성을 추가하기 위해 상속받는 작은 클래스"다.

```cpp
class Button : public Box, public Label, public Tooltip {};
```

`Box`, `Label`, `Tooltip` 세 믹스인을 조합해서 완전한 UI 요소를 만드는 식이다. 믹스인은 가상 함수(Ch.25에서 다룰 예정)를 쓰는 복잡한 다형적 계층보다는, **템플릿과 함께 쓰는 편이 더 잘 맞는다** — 유연한 조합이 필요하면서도 다형성 오버헤드는 필요 없는 경우가 많기 때문이다.

### 권장 사항

> "다른 대안이 오히려 더 복잡해지는 경우가 아니라면 다중 상속을 피하라."

다중 상속으로 풀 수 있는 문제 대부분은 단일 상속만으로도 해결 가능하다. 믹스인이나 인터페이스류 설계처럼 목적이 뚜렷한 경우에 한해 전략적으로 쓰는 게 권장된다.

### 자주 하는 실수 TOP 5

1. **파생 클래스 생성자에서 기반 클래스 생성자를 호출하지 않기** — 상속받은 멤버가 초기화되지 않은 채 남는다.
2. **상속받은 멤버를 파생 클래스 멤버 초기화 목록에서 직접 초기화하려다 컴파일 에러** — 반드시 기반 클래스 생성자를 거쳐야 한다.
3. **재정의 함수 안에서 스코프 없이 자기 이름을 호출** — `Base::` 없이 부르면 무한 재귀에 빠진다.
4. **파생 클래스가 오버로드 하나만 재정의하고 `using Base::func;`를 빠뜨리기** — 기반 클래스의 나머지 오버로드가 통째로 가려진다.
5. **다중 상속에서 다이아몬드 구조를 만들고도 모호성을 방치** — 이름 충돌 시 `Class::func()`로 명시하지 않으면 컴파일 에러가 난다.
