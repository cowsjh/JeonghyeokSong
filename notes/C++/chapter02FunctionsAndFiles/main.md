## 1. 함수를 쓰는 이유

### 코드 중복의 문제

같은 작업을 여러 곳에서 해야 할 때 코드를 복사해 붙여넣으면 어떻게 될까?

```cpp
// 나쁜 코드
int main()
{
    // 각도 계산 — 3번 반복
    double angle1 { jointPos1 * 3.14159 / 180.0 };
    double angle2 { jointPos2 * 3.14159 / 180.0 };
    double angle3 { jointPos3 * 3.14159 / 180.0 };
    // ...
}
```

`3.14159`를 더 정확한 값으로 바꾸고 싶다면? 세 군데를 다 찾아서 고쳐야 한다.  
하나라도 빠뜨리면 버그. 이것이 **DRY 원칙(Don't Repeat Yourself)** 을 지켜야 하는 이유다.

### 함수로 해결

```cpp
double degreesToRadians(double degrees)
{
    return degrees * 3.14159 / 180.0;
}

int main()
{
    double angle1 { degreesToRadians(jointPos1) };
    double angle2 { degreesToRadians(jointPos2) };
    double angle3 { degreesToRadians(jointPos3) };
}
```

이제 변환식을 고치려면 `degreesToRadians` 함수 한 곳만 수정하면 된다.

### 함수가 주는 3가지 이점

1. **재사용** — 같은 코드를 여러 곳에서 쓸 수 있다
2. **모듈화** — 복잡한 프로그램을 작고 이해하기 쉬운 단위로 분리
3. **테스트** — 함수 단위로 독립적 검증이 가능하다

### 함수 호출의 동작 원리

```cpp
void doPrint()
{
    std::cout << "doPrint 실행 중\n";
}

int main()
{
    std::cout << "main 시작\n";
    doPrint();                        // CPU가 현재 위치를 저장하고 doPrint로 이동
    std::cout << "main 계속\n";     // doPrint 끝나면 여기로 돌아옴
    return 0;
}
```

출력:
```
main 시작
doPrint 실행 중
main 계속
```

CPU는 함수를 호출할 때 "돌아올 주소"를 저장해두고 함수로 점프한다.  
함수가 끝나면 저장해둔 주소로 되돌아와 다음 문장을 실행한다.

> ROS2의 콜백 함수도 같은 원리다. 메시지가 도착하면 ROS가 등록된 콜백을 호출하고,  
> 콜백이 끝나면 제어권이 다시 ROS 실행 루프로 돌아간다.

## 2. 함수 반환값

### 계산 결과를 호출자에게 전달하는 방법

함수가 작업을 수행한 결과를 밖으로 꺼낼 방법이 없으면, 계산이 함수 안에 갇혀버린다.  
**반환값(return value)** 은 함수가 호출자에게 결과를 돌려주는 메커니즘이다.

```cpp
int add(int x, int y)
{
    return x + y;   // 계산 결과를 호출자에게 돌려줌
}

int main()
{
    int result { add(3, 4) };          // 7이 반환되어 result에 저장됨
    std::cout << result << '\n';       // 7

    std::cout << add(1, 2) << '\n';   // 반환값을 직접 사용 가능
    std::cout << add(1, 2) + 10 << '\n'; // 표현식에 포함도 가능
    return 0;
}
```

### 반환 타입과 return 문

함수 이름 앞에 오는 타입이 반환 타입이다. `return` 뒤의 값이 실제로 반환되는 값이다.

```cpp
int getAge()          // 반환 타입: int
{
    return 25;        // 25를 반환
}

double getGravity()   // 반환 타입: double
{
    return 9.8;
}
```

반환 타입과 실제 반환값의 타입이 다르면 **자동 변환**이 일어나거나 컴파일 에러가 난다.

### void 함수 — 반환값 없음

반환할 값이 없을 때 반환 타입을 `void`로 선언한다.  
`void` 함수는 `return;`만 쓰거나 아예 생략할 수 있다.

```cpp
void printMessage(std::string msg)
{
    std::cout << msg << '\n';
    // return 없어도 됨
}
```

### main()의 return 0

`main()`은 프로그램 종료 상태를 운영체제에 반환한다.  
`0`은 정상 종료, 0이 아닌 값은 오류를 의미한다.  
`main()`에서 `return`을 생략하면 컴파일러가 자동으로 `return 0;`을 넣어준다.

## 3. 함수 매개변수와 인수

### 외부 데이터를 함수 안으로 가져오는 방법

함수가 고정된 값만 다룬다면 재사용성이 없다.  
**매개변수(parameter)** 는 함수가 호출자로부터 데이터를 받는 창구다.

```
           인수(argument)
              ↓
add(3, 4)  ──────→  int add(int x, int y)
                               ↑
                         매개변수(parameter)
```

- **매개변수**: 함수 선언부의 변수 (`int x`, `int y`)
- **인수**: 호출 시 실제로 전달하는 값 (`3`, `4`)

### Pass by Value — 복사본으로 작업한다

인수가 매개변수로 전달될 때 **값이 복사**된다.  
함수 안에서 매개변수를 바꿔도 **원본 변수는 변하지 않는다.**

```cpp
void doubleIt(int x)
{
    x = x * 2;   // 복사본을 바꿈
    std::cout << "함수 안: " << x << '\n';
}

int main()
{
    int value { 5 };
    doubleIt(value);
    std::cout << "함수 밖: " << value << '\n'; // 여전히 5
}
```

출력:
```
함수 안: 10
함수 밖: 5
```

이것이 의도적인 설계다. 함수가 원본을 실수로 망가뜨리는 일을 막는다.  
원본을 바꾸고 싶을 때는 참조자(`&`)나 포인터를 쓴다 (이후 챕터에서 다룸).

## 4. 지역 변수와 스코프

### 지역 변수란?

함수 내부에서 정의된 변수를 **지역 변수(local variable)** 라 한다.  
함수가 시작할 때 생성되고, 함수가 끝나면 **소멸한다.**

```cpp
void myFunction()
{
    int x { 5 };     // 이 함수 안에서만 존재
    std::cout << x;
}  // 여기서 x 소멸

int main()
{
    myFunction();
    // std::cout << x;  // 컴파일 에러 — x는 이 스코프에 없음
}
```

### 스코프 (Scope)

변수가 유효한(접근 가능한) 코드 영역을 **스코프(scope)** 라 한다.  
중괄호 `{}`가 스코프의 경계를 만든다.

```cpp
int main()
{
    int x { 10 };           // x의 스코프 시작

    {
        int y { 20 };       // y의 스코프 시작
        std::cout << x;     // OK — x는 이 스코프에서 보임
        std::cout << y;     // OK
    }                       // y의 스코프 종료 — y 소멸

    std::cout << x;         // OK
    // std::cout << y;      // 에러 — y는 이미 소멸
    return 0;
}                           // x의 스코프 종료
```

### 같은 이름이어도 다른 변수

서로 다른 함수의 지역 변수는 이름이 같아도 완전히 별개다.

```cpp
void functionA()
{
    int x { 1 };
}

void functionB()
{
    int x { 2 };  // functionA의 x와 무관
}
```

## 5. 전방 선언 — 선언 vs 정의

### 컴파일러는 위에서 아래로 읽는다

컴파일러는 소스코드를 위에서 아래로 순서대로 읽는다.  
함수를 호출하는 코드가 함수 정의보다 **위에** 있으면 컴파일러는 그 함수를 모른다.

```cpp
#include <iostream>

int main()
{
    std::cout << add(3, 4) << '\n';  // 컴파일 에러! add가 뭔지 모름
    return 0;
}

int add(int x, int y)  // 이게 밑에 있어서 위에서 못 씀
{
    return x + y;
}
```

### 해결책 1 — 순서 바꾸기

```cpp
int add(int x, int y) { return x + y; }  // 먼저 정의

int main()
{
    std::cout << add(3, 4) << '\n';  // 이제 OK
}
```

하지만 함수가 서로를 호출하거나, 파일이 여러 개이거나, 코드를 원하는 순서로 정리하고 싶을 때는 순서 변경이 불가능하다.

### 해결책 2 — 전방 선언 (Forward Declaration)

함수의 **선언(declaration)** 만 먼저 올려두면, 컴파일러에게 "이 함수가 존재한다"고 미리 알릴 수 있다.

```cpp
int add(int x, int y);  // 전방 선언 — 함수 본체 없이 존재만 알림

int main()
{
    std::cout << add(3, 4) << '\n';  // OK — 컴파일러가 add의 존재를 앎
    return 0;
}

int add(int x, int y)  // 나중에 실제 정의
{
    return x + y;
}
```

### 선언(Declaration) vs 정의(Definition)

| 용어 | 의미 | 메모리 할당 |
|------|------|-----------|
| **선언** | "이런 이름의 것이 있다"고 컴파일러에게 알림 | 없음 |
| **정의** | 실제 구현/생성 | 있음 |

정의는 선언을 포함한다. 즉 모든 정의는 선언이기도 하다.

```cpp
int add(int x, int y);       // 순수 선언 (함수 원형, prototype)
int add(int x, int y) { ... } // 정의 (선언 + 구현)

int x;                        // 정의 (변수 생성, 메모리 할당)
extern int x;                 // 선언만 (다른 파일의 x가 있음을 알림)
```

## 6. 여러 파일로 이루어진 프로그램

### 왜 파일을 나누는가?

프로그램이 커지면 모든 코드를 파일 하나에 넣는 것이 불가능해진다.  
파일을 역할별로 나누면:

- **변경된 파일만 재컴파일** — 파일 전체를 다시 컴파일하지 않아도 됨
- **역할 분리** — 각 파일이 하나의 책임을 가짐
- **팀 협업** — 여러 사람이 서로 다른 파일을 동시에 작업 가능

### 컴파일과 링크의 두 단계

파일이 여러 개일 때 빌드는 두 단계로 일어난다.

```
[컴파일 단계]
add.cpp  ──컴파일──→  add.o  (오브젝트 파일)
main.cpp ──컴파일──→  main.o

[링크 단계]
add.o + main.o ──링크──→  실행 파일
```

**컴파일러**는 각 `.cpp` 파일을 **독립적으로** 컴파일한다. 다른 파일의 내용을 모른다.  
**링커**가 컴파일된 오브젝트 파일들을 하나로 엮어 실행 파일을 만든다.

컴파일러·링커 개념 자체는 [Chapter 0 — Introduction (시작하기 전에)](../chapter00Introduction/main.md) 4절에서 먼저 다뤘다.

### 파일 간 함수 호출 — 전방 선언이 필요한 이유

`main.cpp`가 `add.cpp`의 `add` 함수를 쓰려 할 때,  
컴파일러는 `main.cpp`만 보고 있으므로 `add`가 뭔지 모른다.  
이때 전방 선언으로 컴파일러에게 알려야 한다.

```
add.cpp          main.cpp
┌──────────┐    ┌─────────────────────┐
│ int add  │    │ int add(int, int);  │ ← 전방 선언
│ (x, y)  │    │                     │
│ { ... }  │    │ int main() {        │
└──────────┘    │   add(3, 4);       │
     ↑          │ }                   │
     └──────────┴─────────────────────┘
          링커가 연결
```

실제로는 헤더 파일로 전방 선언을 관리한다 (9절 참고).

### 빌드 명령 예시

```bash
# 두 파일을 함께 컴파일하여 실행 파일 생성
g++ main.cpp add.cpp -o program

# ROS2에서는 CMakeLists.txt가 이 과정을 자동으로 처리
```

## 7. 네임스페이스와 이름 충돌

### 이름 충돌이 왜 문제인가?

프로그램이 커지고 여러 라이브러리를 쓰다 보면 같은 이름의 함수가 충돌할 수 있다.

```cpp
// 내가 만든 함수
void print(int x) { std::cout << x; }

// 외부 라이브러리 함수 (같은 이름!)
void print(int x) { /* 다른 구현 */ }
```

링커가 어느 `print`를 써야 할지 몰라 **링커 에러**가 난다.

### 네임스페이스 — 이름을 격리하는 공간

**네임스페이스(namespace)** 는 이름들을 별도 영역에 가둬서 충돌을 방지하는 메커니즘이다.  
같은 이름이어도 다른 네임스페이스에 있으면 별개로 취급된다.

```
std::cout     →  std 네임스페이스 안의 cout
my::print     →  my 네임스페이스 안의 print
```

`::` 연산자가 "어느 네임스페이스의"를 표현한다.

### std:: 가 붙는 이유

C++ 표준 라이브러리의 모든 기능은 `std` 네임스페이스 안에 있다.  
`cout`, `cin`, `string` 등이 전부 `std::` 안에 있어서 우리가 만든 이름과 충돌하지 않는다.

```cpp
std::cout  // 표준 라이브러리의 cout
std::cin   // 표준 라이브러리의 cin
std::string // 표준 라이브러리의 string
```

### using namespace std — 왜 쓰면 안 되는가

`using namespace std;`를 쓰면 `std::` 없이 `cout`, `cin` 등을 바로 쓸 수 있다.  
편해 보이지만 위험하다.

```cpp
using namespace std;

int count { 5 };  // 내 변수
// std에도 count가 있다면? 충돌!
```

나중에 추가된 라이브러리나 표준이 같은 이름을 사용하면 기존 코드가 갑자기 깨진다.  
찾기도 어렵고 수정도 어려운 버그가 생긴다.

> **규칙**: `using namespace std;`는 절대 쓰지 마라. 항상 `std::` 를 명시해라.

## 8. 전처리기와 #include

### 컴파일 전에 일어나는 일

C++ 소스코드가 컴파일되기 전에 **전처리기(preprocessor)** 가 먼저 실행된다.  
전처리기는 `#`으로 시작하는 지시문(**전처리 지시문, preprocessor directive**)을 처리한다.

### #include 의 동작 원리

`#include`는 "지정한 파일의 내용을 이 자리에 통째로 복사해줘"라는 지시다.

```cpp
#include <iostream>
// 실제로는 iostream 파일의 수천 줄 내용이 여기에 복사됨
```

- `<꺾쇠괄호>`: 컴파일러가 설치된 표준 라이브러리 폴더에서 찾음
- `"큰따옴표"`: 현재 소스 파일 폴더에서 먼저 찾고, 없으면 표준 라이브러리 폴더에서 찾음

```cpp
#include <iostream>   // 표준 라이브러리
#include "myfile.h"   // 내가 만든 헤더
```

### 매크로 (#define)

`#define`은 텍스트 치환을 수행한다.

```cpp
#define MAX_SIZE 100
// 컴파일 전에 코드 전체의 MAX_SIZE가 100으로 치환됨
```

매크로는 타입 안전성이 없고 디버깅이 어려워 현대 C++에서는 `const`/`constexpr`로 대체한다.

## 9. 헤더 파일

### 왜 헤더 파일이 필요한가?

파일이 여러 개인 프로젝트에서 `add` 함수를 여러 파일이 써야 한다고 하자.  
각 파일마다 전방 선언을 복사해 넣는 방식은 파일이 늘어날수록 관리가 불가능해진다.

**헤더 파일(.h)** 은 선언들을 한 곳에 모아두고, 필요한 파일에서 `#include`로 가져다 쓰는 방법이다.

```
add.h        → 선언 모음 (add 함수가 있다고 알림)
add.cpp      → add 함수의 실제 구현
main.cpp     → add.h를 include해서 add 함수 사용
```

### 예제 — 3파일 구조

**add.h**
```cpp
// 선언만 있음 — 구현 없음
int add(int x, int y);
```

**add.cpp**
```cpp
#include "add.h"       // 자신의 헤더를 포함 (선언과 정의 일치 확인용)

int add(int x, int y)  // 실제 구현
{
    return x + y;
}
```

**main.cpp**
```cpp
#include "add.h"       // add의 선언을 가져옴
#include <iostream>

int main()
{
    std::cout << add(3, 4) << '\n';  // OK
    return 0;
}
```

### 헤더 가드 (Header Guard)

같은 헤더가 두 번 이상 포함되면 선언이 중복되어 에러가 난다.  
**헤더 가드**는 이를 방지하는 패턴이다.

```cpp
#ifndef ADD_H   // ADD_H가 정의 안 됐으면
#define ADD_H   // ADD_H를 정의하고 아래 내용 포함

int add(int x, int y);

#endif          // ADD_H 블록 끝
```

처음 포함될 때 `ADD_H`가 정의된다. 두 번째 포함 시 `#ifndef`가 false가 되어 내용을 건너뛴다.

현대 컴파일러에서는 `#pragma once`로 같은 효과를 더 간단하게 낼 수 있다.

```cpp
#pragma once

int add(int x, int y);
```

### 헤더에 정의(구현)를 넣으면 안 되는 이유

헤더가 여러 파일에 include되면, 그 안의 **정의도 여러 번 복사**된다.  
같은 함수의 정의가 여러 번 나타나면 **ODR(One Definition Rule)** 위반으로 링커 에러가 난다.

헤더에는 **선언만**, 구현은 `.cpp` 파일에 써라.

> ROS2 패키지에서도 이 구조를 그대로 쓴다.  
> `include/` 폴더의 `.hpp` 파일에 선언, `src/` 폴더의 `.cpp` 파일에 구현.

## 10. 프로그램 설계 방법론

### 코딩보다 설계가 먼저다

처음 프로그래밍을 배우면 아이디어가 생기자마자 바로 코딩을 시작하고 싶어진다.  
하지만 설계 없이 코딩을 시작하면 중간에 방향을 잃거나 처음부터 다시 짜야 하는 일이 자주 생긴다.

### 설계 단계

**1. 목표 정의** — 프로그램이 정확히 무엇을 해야 하는가?  
**2. 요구사항 명시** — 어떤 입력을 받고 어떤 출력을 내야 하는가? 제약 조건은?  
**3. 문제 분해** — 큰 문제를 작은 단위로 쪼갠다

```
[큰 문제]
"2-DOF 로봇팔 제어기 만들기"
        ↓
[하위 문제들]
- 목표 위치 입력 받기
- 역기구학 계산
- 관절 각도 → PWM 변환
- 모터 드라이버로 명령 전송
```

**4. 단계별 구현 + 테스트** — 전체를 한 번에 짜지 말고, 하위 문제 하나씩 구현하고 테스트한다

### 구현 순서

```
1. main() 함수 뼈대 작성 (주석으로 흐름만 표현)
2. 가장 단순한 하위 문제부터 구현
3. 각 함수를 구현할 때마다 바로 테스트
4. 전체 통합 테스트
```

```cpp
int main()
{
    // 1. 목표 위치 입력
    // 2. 역기구학 계산
    // 3. 관절 명령 전송
    return 0;
}
```

처음엔 주석으로만 구조를 잡고, 하나씩 채워나간다.

### 핵심 원칙

- **단순하게 시작** — 완벽한 구현보다 동작하는 단순한 버전 먼저
- **점진적으로 추가** — 기본이 동작하면 기능을 하나씩 추가
- **자주 테스트** — 한꺼번에 많이 짜고 테스트하면 버그를 찾기 어렵다

## 핵심 요약 카드

| 개념 | 핵심 내용 |
|------|----------|
| 함수 | 재사용 가능한 문장 묶음 — DRY 원칙 |
| 반환값 | 함수 결과를 호출자에게 전달 — `void`는 반환값 없음 |
| Pass by Value | 인수가 복사됨 — 함수 안에서 바꿔도 원본 불변 |
| 지역 변수 | 함수가 끝나면 소멸 — 함수 밖에서 접근 불가 |
| 전방 선언 | 함수 존재를 먼저 알림 — 정의는 나중에 가능 |
| 선언 vs 정의 | 선언=존재 알림, 정의=실제 구현 (모든 정의는 선언) |
| 네임스페이스 | 이름 충돌 방지 — `std::`는 표준 라이브러리 네임스페이스 |
| `using namespace std` | 절대 쓰지 마라 — 미래 이름 충돌 위험 |
| `#include` | 지정 파일 내용을 해당 위치에 복사 |
| 헤더 파일 | 선언을 중앙 관리 — 구현은 `.cpp`에 |
| 헤더 가드 | 중복 포함 방지 — `#pragma once` 또는 `#ifndef` 패턴 |
| 컴파일 vs 링크 | 컴파일=파일별 변환, 링크=오브젝트 파일 연결 |
| 설계 우선 | 코딩 전 문제 분해 → 단순 구현 → 점진적 확장 |

### 자주 하는 실수 TOP 5

1. 함수 정의가 호출보다 아래에 있음 → 컴파일 에러. **전방 선언 추가 또는 순서 변경**
2. `using namespace std;` 사용 → 이름 충돌 위험. **항상 `std::` 명시**
3. 헤더에 함수 구현 작성 → ODR 위반 링커 에러. **헤더엔 선언만, 구현은 .cpp**
4. 헤더 가드 없는 헤더 → 중복 포함 시 에러. **`#pragma once` 항상 추가**
5. Pass by value 착각 → "함수가 내 변수를 바꿨는데?" **복사본을 바꾸는 것, 원본 불변**
