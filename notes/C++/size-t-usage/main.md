# size_t를 쓰는 이유 (unsigned + 플랫폼 폭 자동 추종)

ROS2 Talker 노드의 `size_t count_ = 0;` 한 줄에서 출발한 질문 — "개수 세는 변수인데 왜 `int`도 `unsigned int`도 아니고 굳이 `size_t`냐".

## `size_t`가 뭔가

이름부터 풀면 "**size**" + "**_t**(type)"다. `_t` 접미사는 C 시절부터 내려온 관례로 "이 이름은 변수가 아니라 타입이다"라는 신호다(`uint8_t`, `pid_t`, `rcl_ret_t` 다 같은 계열). 그러니까 `size_t`는 "크기를 나타내는 타입"이라는 뜻 그대로다.

정체를 보면 사실 독립된 새 타입이 아니라 `typedef`로 만든 **별명**이다:

```cpp
// 플랫폼마다 실제 정의는 다름 (개념적으로)
typedef unsigned long size_t;   // 64비트 리눅스에서 흔한 형태
```

즉 컴파일러/OS가 "이 플랫폼에서 메모리 크기를 표현하기 충분한 unsigned 정수가 뭐냐"를 판단해서 그걸 `size_t`라는 이름 뒤에 숨겨둔 것이다.

## 왜 쓰나 — 두 가지 축

**① 개수/크기는 절대 음수가 아니다 (unsigned)**
개수가 -1이 될 일은 없다. `int`(음수 포함) 대신 음수 없는 정수를 써서 "이 값은 절대 음수가 될 리 없다"는 의도를 타입으로 못박는다.

**② 그중에서도 왜 `unsigned int`가 아니라 `size_t`인가 — 시스템 폭을 자동으로 따라가니까**
`size_t`는 "이 시스템에서 표현 가능한 가장 큰 메모리 객체의 크기까지 담을 수 있어야 한다"는 목적으로 태어났다. 그래서 [시스템의 주소 폭](../32-64bit-systems/main.md)(=포인터 크기)을 그대로 따라간다:

- 32비트 시스템 → `size_t`는 32비트(4바이트)
- 64비트 시스템 → `size_t`는 64비트(8바이트)

반면 `unsigned int`는 64비트 시스템에서도 하위 호환성 때문에 대개 32비트로 박제돼 있다. 그래서 배열 크기·인덱스·`sizeof`·`std::vector::size()` 같은 "크기/개수"를 다루는 표준 라이브러리가 전부 `size_t`를 채택했고, "개수/크기를 셀 땐 `size_t`를 쓴다"가 C++ 관습으로 굳었다.

## Talker의 `count_`엔 사실 어느 쪽이든 실무 차이는 없다

500ms마다 하나씩 세는 카운터라 `unsigned int`(약 43억까지)를 써도 실질적으로 안 넘친다 — 43억 번 보내려면 수십 년이 걸린다. 그럼에도 `size_t`를 쓴 건 관용적 스타일을 따른 것이고, 나중에 `std::vector`의 `.size()`나 배열 인덱싱처럼 `size_t`가 아니면 타입이 안 맞는 상황과 자연스럽게 맞물리게 하려는 습관이다.

한 줄 요약: **`size_t` = 개수/크기 용도로 표준화된, 시스템 최대 메모리 범위까지 커버하는 unsigned 정수 타입.** 음수 방지(①)와 시스템 규모에 맞춰 자동으로 커지는 크기 보장(②)을 한 이름에 압축한 것.
