## 1. 프로그래밍 언어의 종류

### CPU는 오직 기계어만 이해한다

CPU가 실제로 실행하는 명령어는 0과 1로 이루어진 **기계어(machine language)** 뿐이다.  
초창기 프로그래머들은 0과 1을 직접 입력했다. 극도로 불편하고 오류가 잦았다.

### 언어의 진화 — 추상화 수준이 높아질수록 편해진다

```
기계어 (Machine Language)
  0100 1000 1000 0011 ...
       ↑ CPU가 직접 실행, 사람이 읽기 거의 불가능

어셈블리 (Assembly)
  MOV RAX, 5
  ADD RAX, RBX
       ↑ 기계어와 1:1 대응, 그나마 읽을 수 있음
       ↑ 어셈블러가 기계어로 변환

고수준 언어 (High-level Language)
  int result = a + b;
       ↑ 사람의 언어에 가까움
       ↑ 컴파일러가 기계어로 변환
```

### 컴파일 vs 인터프리트

고수준 언어를 기계어로 변환하는 방식은 두 가지다.

| 방식 | 설명 | 예시 |
|------|------|------|
| **컴파일** | 소스코드 전체를 미리 기계어로 변환 → 실행파일 생성 | C, C++, Rust |
| **인터프리트** | 소스코드를 한 줄씩 즉시 실행 | Python, JavaScript |

C++은 컴파일 언어다. 미리 변환해두기 때문에 **실행 속도가 빠르다**.  
로보틱스에서 실시간 제어(1ms 주기 루프)를 C++로 구현하는 핵심 이유다.

## 2. C와 C++ 소개

### C의 탄생

C는 1972년 Dennis Ritchie가 Bell Labs에서 만들었다.  
당시 대부분의 프로그램은 어셈블리로 짰는데, 어셈블리는 CPU마다 달라서 다른 기종에서는 다시 짜야 했다.

C는 **고수준 언어이면서도 하드웨어에 가까운 제어**가 가능한 절충점으로 설계됐다.  
오늘날도 운영체제 커널, 임베디드 시스템에서 여전히 핵심으로 쓰인다.

### C++의 탄생 — C에 무엇을 더했나?

C++은 1983년 Bjarne Stroustrup이 C를 기반으로 만들었다. 이름의 `++`는 C를 한 단계 발전시켰다는 의미다.

핵심 추가 사항:
- **객체지향 프로그래밍(OOP)** — 클래스, 상속, 다형성
- **제네릭 프로그래밍** — 템플릿
- **표준 라이브러리** — STL (벡터, 맵 등)
- **예외 처리** — try/catch

C++은 C와 **하위 호환**된다. 대부분의 C 코드는 C++ 컴파일러로 컴파일된다.

### 왜 C++인가?

| 언어 | 특징 | 단점 |
|------|------|------|
| Python | 쉽고 빠른 개발 | 느림, 실시간 제어 부적합 |
| Java | 플랫폼 독립적 | 가비지 컬렉션으로 지연 예측 불가 |
| **C++** | **빠름, 하드웨어 제어, 풍부한 생태계** | 배우기 어려움 |

ROS2의 핵심 구현체인 `rclcpp`가 C++인 이유가 여기 있다.  
1ms 주기 제어 루프, 센서 드라이버, 실시간 연산 — 전부 C++의 영역이다.

### C++ 표준의 발전

| 표준 | 연도 | 주요 추가 사항 |
|------|------|-------------|
| C++98 | 1998 | 최초 표준화 |
| C++11 | 2011 | `auto`, 람다, `nullptr`, 스마트 포인터 |
| C++14 | 2014 | C++11 개선 |
| C++17 | 2017 | `if constexpr`, 구조적 바인딩 |
| C++20 | 2020 | 모듈, 코루틴, Concepts |
| C++23 | 2023 | 최신 표준 |

## 3. C++ 개발 7단계 프로세스

### 코드 작성은 3단계에서 시작한다

프로그램을 만드는 과정은 코딩보다 훨씬 크다. 좋은 프로그래머일수록 코딩 전 단계에 더 많은 시간을 쓴다.

```
1단계: 문제 정의
   "무엇을 만들 것인가?" 를 명확히
   └─ 막연한 목표 → 실패의 씨앗

2단계: 해결 방안 결정
   "어떻게 풀 것인가?" 설계
   └─ 좋은 설계: 직관적, 문서화, 모듈화, 오류 처리 포함

3단계: 프로그램 작성
   소스 코드 작성 (코드 에디터 사용)
   └─ 파일명: main.cpp 권장

4단계: 컴파일
   컴파일러가 소스코드 → 기계어(오브젝트 파일) 변환

5단계: 링크
   링커가 오브젝트 파일들 + 라이브러리 → 실행파일

6단계: 테스트
   프로그램이 의도대로 작동하는지 검증

7단계: 디버깅
   버그 발견 시 수정 후 4단계부터 반복
```

### "버그(bug)"의 유래

1947년 그레이스 호퍼가 하버드 Mark II 컴퓨터를 디버깅하던 중 실제 나방(moth)이 릴레이에 끼어 오작동을 일으킨 것을 발견했다.  
이후 프로그램 오류를 "bug"라 부르게 됐다.

### 왜 설계가 먼저인가?

소프트웨어 유지보수에는 전체 개발 비용의 **60~90%** 가 소요된다.  
초기에 설계를 잘못 잡으면 나중에 고치는 비용이 기하급수적으로 커진다.

## 4. 컴파일러, 링커, 라이브러리

### 소스코드가 실행파일이 되는 과정

```
소스 파일들 (.cpp)
    │
    ▼ [컴파일러]
    │  - C++ 문법 검사
    │  - 소스코드 → 기계어 변환
    │
오브젝트 파일들 (.o / .obj)
    │
    ▼ [링커]
    │  - 오브젝트 파일들 연결
    │  - 라이브러리 연결
    │  - 파일 간 함수 참조 해결
    │
실행 파일 (.exe / 바이너리)
```

### 컴파일러의 역할

**컴파일러(compiler)** 는 `.cpp` 파일 하나씩을 독립적으로 처리한다.

- C++ 문법이 맞는지 검사 — 틀리면 **컴파일 에러**
- 문법은 맞지만 의심스러운 코드 — **경고(warning)**
- 문법 통과 시 → 기계어로 된 **오브젝트 파일(.o)** 생성

### 링커의 역할

**링커(linker)** 는 여러 오브젝트 파일을 하나의 실행파일로 엮는다.

- `main.cpp`에서 `add()` 함수를 호출했고, `add.cpp`에 정의가 있다면?  
  → 링커가 두 파일을 연결해서 서로 찾을 수 있게 만든다.
- 연결에 실패하면 **링커 에러** 발생

### 라이브러리

**라이브러리(library)** 는 미리 컴파일된 코드 묶음이다.

- **C++ 표준 라이브러리**: `iostream`, `vector`, `string` 등 — 항상 자동 연결
- **써드파티 라이브러리**: 직접 설치하고 링커에 알려줘야 함

> ROS2도 라이브러리다. `rclcpp`, `geometry_msgs` 등을 `CMakeLists.txt`에 등록하면  
> 링커가 내 코드와 ROS2 코드를 연결해준다.

컴파일과 링크를 실제 코드로 실습해보는 예제는 [Chapter 2 — Functions and Files (함수와 파일)](../chapter02FunctionsAndFiles/main.md)에서 다룬다.

## 5. IDE 설치 및 첫 프로그램

### IDE가 필요한 이유

**IDE(Integrated Development Environment)** 는 코드 에디터 + 컴파일러 + 디버거를 하나로 묶은 도구다.  
메모장으로 코드를 쓰고 터미널에서 직접 컴파일할 수도 있지만, IDE가 훨씬 생산적이다.

| 기능 | 없을 때 | IDE 있을 때 |
|------|---------|------------|
| 에러 표시 | 컴파일 후 터미널 확인 | 타이핑 중 실시간 표시 |
| 자동완성 | 직접 타이핑 | 함수명 자동 제안 |
| 디버깅 | `cout` 찍어가며 확인 | 중단점으로 실행 중 변수 확인 |

**Windows 환경 추천 IDE:**
- **Visual Studio 2022** (Community) — 가장 강력, Windows 특화
- **VS Code + 확장** — 가벼움, 크로스플랫폼

### 첫 프로그램 — Hello World

```cpp
#include <iostream>

int main()
{
    std::cout << "Hello, world!" << '\n';
    return 0;
}
```

**각 줄이 하는 일:**

| 코드 | 역할 |
|------|------|
| `#include <iostream>` | 입출력 라이브러리를 이 파일에 포함 |
| `int main()` | 프로그램 시작점 함수 선언 |
| `std::cout << "Hello, world!"` | 콘솔에 문자열 출력 |
| `return 0;` | 운영체제에 "정상 종료" 신호 |

## 6. 흔한 C++ 문제들

### 컴파일 에러 유형

**`undeclared identifier` 에러 — `std::` 또는 `#include` 누락**

```cpp
cout << "Hello";           // 에러: cout이 뭔지 모름
std::cout << "Hello";      // OK: std 네임스페이스 명시
```

혹은 `#include <iostream>`을 파일 맨 위에 추가했는지 확인.

**`unresolved external symbol _main` — main() 함수 없음**

모든 C++ 프로그램에는 `main()` 함수가 반드시 있어야 한다.  
오타(`Main()`, `MAIN()`)도 같은 에러를 낸다.

**C++17/20 기능을 C++11에서 쓰려 할 때**

언어 표준을 컴파일러에 맞게 설정해야 한다 (10절 참고).

### 런타임 문제

**콘솔 창이 바로 닫힘**

IDE에서 "디버그 없이 실행"이 아닌 **"디버그로 실행"** 을 쓰면 결과를 볼 수 있다.  
또는 프로그램 끝에 아래를 추가:

```cpp
std::cin.get(); // 엔터 누를 때까지 대기
```

**Visual Studio — C1010 에러 (`pch.h` 관련)**

프리컴파일드 헤더 설정 문제다. 프로젝트 속성에서 "미리 컴파일된 헤더" 항목을 "사용 안 함"으로 설정.

## 7. 빌드 설정 — Debug vs Release

### 같은 코드, 다른 빌드

소스코드는 하나지만 컴파일 방식에 따라 완전히 다른 실행파일이 나온다.

| 항목 | Debug | Release |
|------|-------|---------|
| 목적 | 개발 중 디버깅 | 최종 배포 |
| 최적화 | 비활성화 | 최대 활성화 |
| 디버깅 정보 | 포함 | 미포함 |
| 파일 크기 | 큼 (예: 65KB) | 작음 (예: 12KB) |
| 실행 속도 | 느림 | 빠름 |

### 왜 Debug에서 최적화를 끄는가?

컴파일러 최적화는 코드를 **재배치하거나 합치거나 제거**한다.  
최적화된 코드는 소스코드와 실행 순서가 달라져서 **디버거로 추적하기 어렵다.**

Debug 모드에서는 "소스코드 한 줄 = 실행파일 한 단계"가 보장되어 정확한 디버깅이 가능하다.

> **규칙**: 개발 중에는 Debug, 성능 측정이나 배포할 때는 Release.  
> ROS2 개발 시 `colcon build --cmake-args -DCMAKE_BUILD_TYPE=Release`로 Release 빌드 가능.

## 8. 컴파일러 확장 비활성화

### 컴파일러 확장이란?

GCC, MSVC, Clang 같은 컴파일러들은 C++ 표준에 없는 **자체 기능(extension)** 을 추가로 지원한다.  
예를 들어 GCC는 가변 길이 배열(VLA)을 지원하지만, 이는 C++ 표준이 아니다.

### 왜 끄는 게 좋은가?

확장 기능을 쓰면 두 가지 문제가 생긴다.

**1. 이식성 문제**: GCC 확장으로 짠 코드가 MSVC에서 컴파일이 안 된다.

```cpp
// GCC 확장 — MSVC에서 컴파일 에러
int n = 10;
int arr[n];  // 표준 C++에서는 배열 크기가 상수여야 함
```

**2. 학습 왜곡**: 확장 기능을 C++ 표준으로 착각하게 된다.  
나중에 다른 환경에서 "왜 안 되지?"라는 상황이 생긴다.

확장을 끄면 내 코드가 **어디서든 동일하게 동작**함을 보장할 수 있다.

**VS Code (g++ 사용 시)** `tasks.json`에 추가:
```json
"-pedantic-errors"
```

## 9. 경고와 에러 레벨 설정

### 경고(Warning)와 에러(Error)의 차이

- **에러**: 문법이 틀려서 컴파일 자체가 불가능 — 반드시 고쳐야 함
- **경고**: 문법은 맞지만 "이거 의도한 건가?" 라고 컴파일러가 묻는 것 — 기술적으로는 통과

```cpp
int x;
std::cout << x;  // 에러는 아님 — 하지만 초기화 안 된 변수를 사용하는 버그
```

### 왜 경고 레벨을 높여야 하는가?

기본 경고 레벨은 매우 낮아서 수많은 잠재적 버그를 그냥 통과시킨다.  
경고 레벨을 높이면 **컴파일러가 더 많은 의심스러운 코드를 지적**해준다.

경고를 에러로 처리하도록 설정하면, **경고가 뜨는 코드는 아예 컴파일이 안 된다.**  
이렇게 하면 "나중에 고치지"가 없어지고 즉시 수정하게 된다.

**VS Code (g++ 사용 시)** `tasks.json`에 추가:

```json
"-Wall",       // 일반적인 경고 모두 활성화
"-Weffc++",    // Effective C++ 스타일 경고
"-Wextra",     // 추가 경고
"-Wsign-conversion",  // 부호 변환 경고
"-Werror"      // 경고를 에러로 처리
```

> 처음에는 경고가 쏟아져서 당황스럽지만, 이 경고들을 고치면서 C++의 함정을 미리 배울 수 있다.  
> 경고를 무시하는 습관은 나중에 찾기 어려운 버그로 이어진다.

## 10. 언어 표준 선택

### C++ 표준이 중요한 이유

C++는 계속 진화한다. 새 표준이 나올 때마다 유용한 기능이 추가되고, 기존 코드가 더 간결해진다.  
컴파일러에게 어느 표준을 기준으로 컴파일할지 알려줘야 한다.

### 어느 표준을 선택해야 하나?

```
개인 학습 / 신규 프로젝트  →  C++17 또는 C++20
회사 프로젝트              →  최신 완성 표준보다 1~2단계 이전 버전
                               (새 표준의 버그가 수정될 시간 필요)
```

**learncpp.com은 C++17을 기준**으로 한다.  
**ROS2 Humble은 C++17**을 지원한다. 이 프로젝트에서는 **C++17로 설정**하면 된다.

### 설정 방법

**VS Code** — `tasks.json`의 `args`에 추가:
```json
"-std=c++17"
```

**CMakeLists.txt (ROS2 패키지)**:
```cmake
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
```

### 표준 확인 매크로

코드에서 현재 적용된 표준을 확인할 수 있다:

```cpp
#include <iostream>

int main()
{
    std::cout << __cplusplus << '\n';
    // C++17이면 201703 출력
    // C++20이면 202002 출력
    return 0;
}
```

## 핵심 요약 카드

| 개념 | 핵심 내용 |
|------|----------|
| 기계어 | CPU가 직접 실행하는 0/1 명령어 — 사람이 직접 쓰지 않음 |
| 컴파일 | 소스코드 전체를 미리 기계어로 변환 → 실행 빠름 |
| C++ | C에 OOP 추가 / 빠름 + 하드웨어 제어 / ROS2의 핵심 언어 |
| 개발 7단계 | 설계(1~3) → 빌드(4~5) → 검증(6~7) / 설계가 먼저 |
| 컴파일러 | `.cpp` → `.o` (기계어 변환, 문법 검사) |
| 링커 | `.o` 파일들 + 라이브러리 → 실행파일 연결 |
| Debug | 최적화 OFF, 디버깅 정보 포함 — 개발 중 사용 |
| Release | 최적화 ON, 크기/속도 최적 — 배포/성능 측정 시 |
| 컴파일러 확장 | 비활성화 — 이식성 보장, 표준 준수 |
| 경고 레벨 | 최대로 올리고 `-Werror`로 경고=에러 처리 |
| 언어 표준 | C++17 선택 — learncpp.com 기준, ROS2 Humble 지원 |

### 자주 하는 실수 TOP 5

1. `std::` 없이 `cout` 사용 → `#include <iostream>` 확인, `std::cout` 으로 써라
2. Debug 모드에서 성능 측정 → 느린 게 당연. **성능 테스트는 Release 빌드**로
3. 컴파일러 경고 무시 → 나중에 찾기 어려운 버그. **경고를 에러로 설정하고 즉시 수정**
4. 컴파일러 확장 기능 사용 → 다른 환경에서 안 됨. **`-pedantic-errors` 추가**
5. C++ 표준 미설정 → 기본값이 구버전. **`-std=c++17` 명시적으로 설정**
