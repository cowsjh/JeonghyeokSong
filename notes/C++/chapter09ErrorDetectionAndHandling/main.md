## 1. 테스트 전략 (9.1)

조건문·사용자 입력이 있는 함수는 가능한 입력 조합이 조 단위로 폭발한다 — 전수 테스트는 애초에 불가능하다. 대신 **"비슷한 입력은 비슷한 결과를 낸다"**는 가정으로 대표 입력만 골라 테스트한다.

- **Unit Testing**: 함수/클래스 단위로 통합 전에 먼저 검증. <mark style="background: #ADCCFFA6;">"작은 단위로 작성 → 자주 컴파일 → 바로 테스트"가 원칙</mark> — 문제를 늦게 발견할수록 수정 비용이 커지기 때문
- **Informal → Preserved → Automated**: 임시 출력 확인 → 테스트 함수로 보존(회귀 확인 가능) → `assert`로 자동 판정(사람이 눈으로 값을 안 봐도 됨)
- **Integration Testing**: 유닛이 각각 통과해도, 합쳤을 때만 드러나는 상호작용 버그가 있어 마지막에 필요

## 2. Code Coverage (9.2)

| 커버리지 종류 | 의미 | 함정 |
|---|---|---|
| Statement coverage | 모든 줄이 한 번은 실행됐는가 | if의 true 분기만 타도 100%가 나올 수 있음 — false 분기 누락을 못 잡음 |
| Branch coverage | if/switch의 **모든 분기**가 실행됐는가 | statement보다 엄격 — 목표는 100% |
| Loop coverage (0-1-2 테스트) | 반복 0회·1회·2회를 각각 테스트 | 2회에서 맞으면 그 이상도 맞다고 간주 가능 — off-by-one을 효율적으로 잡음 |

카테고리별 경계값도 챙긴다: 정수는 음수/0/양수, 부동소수점은 0.1·0.7 같은 정밀도 함정, 문자열은 빈 문자열/공백, 포인터는 null.

### 실제로 어떻게 측정하는가

coverage는 사람이 눈으로 세는 게 아니라 컴파일러/도구가 실행 로그를 분석해서 자동으로 계산한다.

| 툴체인 | 도구 | 방식 |
|---|---|---|
| GCC/g++ | `gcov` | `--coverage` 옵션으로 컴파일 → 실행 → `gcov 파일.cpp`로 줄별 실행 횟수 리포트 (텍스트) |
| MSVC (Visual Studio) | `OpenCppCoverage` | MSVC는 gcov 포맷을 못 읽고, Community Edition엔 내장 coverage 기능이 없음(Enterprise 전용) — 오픈소스 도구를 exe에 씌워 실행하며 HTML 리포트 생성 |

리포트에는 각 줄의 실행 횟수가 찍히는데, **0번 실행된 줄(gcov 기준 `#####`)이 바로 branch coverage 함정의 증거**다 — 예를 들어 `if (y < 0)`의 에러 처리 분기를 한 번도 안 타본 채로 statement coverage가 80%대로 나오는 식. 반대로 그 분기까지 테스트에 포함시켜 100%를 채웠다고 해서 로직 자체가 옳다는 보장은 없다 — coverage는 "실행됐는가"만 알려줄 뿐 "결과가 맞는가"는 여전히 `assert`나 값 검증([5. std::cin의 잘못된 입력 처리 (9.5)](#5-stdcin의-잘못된-입력-처리-95))의 몫이다.

## 3. 흔한 의미 오류 카테고리 (9.3)

**Semantic error = 문법은 맞는데 의도와 다르게 동작.** 컴파일러가 못 잡아주므로 테스트로만 발견된다.

| 유형             | 예시                                                                                                      |                |
| -------------- | ------------------------------------------------------------------------------------------------------- | -------------- |
| 조건 연산자 오사용     | `if (x >= 5)`인데 의도는 `x > 5`                                                                             |                |
| 무한 루프          | `while (count <= 10) { ... }` — 증가문 누락                                                                  |                |
| Off-by-one     | `for (int i{1}; i < 5; ++i)` — `<=`여야 5까지 도는데 4까지만                                                      |                |
| 연산자 우선순위 오해    | `!x > y`는 `(!x) > y`이지 `!(x > y)`가 아님                                                                   |                |
| 부동소수점 정밀도      | `0.1`을 열 번 더해도 `1.0`과 `==` 비교가 실패할 수 있음                                                                 |                |
| 의도치 않은 정수 나눗셈  | `5 / 3`은 `1.667`이 아니라 `1`                                                                               |                |
| Null statement | `if (c == 'y');`의 세미콜론이 빈 문장 — 다음 줄이 무조건 실행 ([Ch.8과 동일 패턴](../chapter08ControlFlow/main.md)) |
| 함수 호출 연산자 누락   | `std::cout << getValue;`는 함수 자체(주소값 취급)를 출력 — `getValue()`가 맞음                                          |                |
| `=` vs `==`    | `if (c = 'y')`는 대입이라 항상 참 ([Ch.8과 동일](../chapter08ControlFlow/main.md))    |

## 4. 함수 안에서 에러 처리하기 (9.4)

함수 내부에서 에러를 만났을 때 선택지:

1. **재시도**: 외부 요인(사용자 입력 등)이면 성공할 때까지 반복
2. **취소/무시**: 문제 있는 로직만 건너뜀 — 단, 호출자가 실패를 모를 수 있으니 진단 출력이나 반환값으로 알려야 함

### 호출자에게 실패를 알리는 방법

```cpp
bool printIntDivision(int x, int y)
{
    if (y == 0) { std::cout << "Error\n"; return false; }
    std::cout << x / y;
    return true;
}
```

`void` 함수를 `bool`로 바꿔 성공 여부를 반환하거나, 반환값이 이미 있다면 **정상 범위 밖의 sentinel 값**을 에러 신호로 쓴다.

### 왜 함수 안에서 std::exit()을 쓰면 안 되는가

중첩 함수 깊은 곳에서 `std::exit()`을 부르면 호출자가 에러 처리 방식을 선택할 기회 자체가 사라진다. **에러는 최대한 `main()`까지 전파해서 상위 로직이 판단하게 해야 한다** — [Ch.8의 halt 규칙](../chapter08ControlFlow/main.md)과 같은 맥락. 예외(exception)가 이 전파를 자동화해주는 더 나은 도구이며 추후 챕터에서 다룬다.

## 5. std::cin의 잘못된 입력 처리 (9.5)

| 문제 유형                                       | 감지                                 | 처리                                                                |
| ------------------------------------------- | ---------------------------------- | ----------------------------------------------------------------- |
| 의미는 없지만 형식은 유효한 입력 (예: `+`,`-`만 받는데 `%` 입력) | 값 자체를 조건으로 검사                      | 루프로 재입력 요청                                                        |
| 잉여 입력 (원하는 값 뒤에 남은 문자)                      | `std::cin.peek()`으로 개행 이전 잔여 문자 확인 | `std::cin.ignore(numeric_limits<streamsize>::max(), '\n')`로 버퍼 비움 |
| 추출 실패 (타입이 안 맞음, 예: 문자를 int로)               | `if (!std::cin)`                   | `std::cin.clear()`로 상태 복구 + 버림줄 처리                                |
| 숫자 오버플로                                     | 추출 실패와 동일하게 감지                     | 추출 실패와 동일한 복구 코드                                                  |

**핵심 함정**: 한 번 추출이 실패하면(fail 상태) `clear()`를 부르기 전까지 **이후의 모든 추출 요청이 조용히 실패**한다 — 에러 메시지 없이 그냥 스킵되므로 디버깅이 까다롭다. 재사용 가능한 복구 함수 패턴:

```cpp
bool clearFailedExtraction()
{
    if (!std::cin)
    {
        if (std::cin.eof()) std::exit(0);
        std::cin.clear();
        ignoreLine();     // 버림
        return true;
    }
    return false;
}
```

## 6. assert와 static_assert (9.6)

### assert — 런타임에 "있으면 안 되는 상태"를 잡는다

```cpp
#include <cassert>
double divide(int x, int y)
{
    assert(y != 0);   // 실패 시 std::abort() + 표현식·파일·줄 번호 출력
    return static_cast<double>(x) / y;
}
```

- **버그(assert) vs 실사용 에러(error handling)의 구분**: assert는 <mark style="background: #ADCCFFA6;">"코드가 맞다면 절대 일어날 수 없는 상태"</mark>를 개발 중에 잡는 용도 — 복구 수단이 없고 그냥 죽는다. 반면 실사용 중 실제로 일어날 수 있는 상황(사용자 입력 등)은 error handling으로 우아하게 처리해야 한다. 둘은 대체재가 아니라 **같은 함수에 둘 다 있을 수 있다**.
- **`NDEBUG` 매크로**가 정의되면(대부분 IDE가 release 빌드에서 자동 설정) assert는 **통째로 컴파일에서 제거**된다 — 런타임 비용 0. 즉 assert에 부작용(실제로 값을 바꾸는 연산)이 있으면 release에서는 그 동작 자체가 사라지는 함정이 생긴다.

### static_assert — 컴파일 타임 버전

```cpp
static_assert(sizeof(int) >= 4, "int must be at least 4 bytes");
```

조건이 **상수 표현식**이어야 하고, 컴파일 시점에 평가되어 실패하면 **빌드 자체가 안 된다**. `NDEBUG`와 무관하게 항상 살아있고, 런타임 비용이 전혀 없다 — [Ch.8의 `if constexpr`](../chapter08ControlFlow/main.md)과 같은 "컴파일 타임에 끝내라" 철학의 연장.

> 로보틱스 연결: `assert(y != 0)` 같은 방어는 IK 솔버의 분모 0 나눗셈, 관절 인덱스 범위 초과 같은 "코드가 맞다면 안 일어나야 할" 상황을 개발 중에 조기 발견하는 데 쓴다. 반면 센서에서 들어오는 실제 입력값 검증은 assert가 아니라 9.5의 에러 처리 방식이어야 한다 — release 빌드에서 assert가 사라지기 때문.

| static_assert                | 컴파일 타임 평가, 항상 살아있음, 런타임 비용 0                                        |
|                              |                                                                     |

### 자주 하는 실수 TOP 3

1. **`std::cin` 추출 실패 후 `clear()` 없이 계속 입력받기** — 이후 모든 입력이 조용히 스킵됨
2. **assert 안에 부작용 있는 코드 넣기** — release 빌드에서 assert 자체가 사라져 그 동작이 통째로 없어짐
3. **branch coverage 없이 statement coverage만 100%로 착각하기** — if의 한쪽 분기만 타도 모든 줄은 "실행됨"으로 잡힘
