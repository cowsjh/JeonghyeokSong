## 1. 함수 포인터

### 왜 필요한가

변수 포인터가 변수의 주소를 담듯, **함수 포인터는 함수의 주소를 담는다.** 함수도 컴파일된 코드가 메모리 어딘가에 있는 이상 주소를 갖기 때문이다. 함수 포인터가 있으면 "어떤 함수를 호출할지"를 런타임에 바꿔 끼울 수 있다 — 정렬 함수에 비교 로직을 바꿔 끼우거나, 콜백을 등록하는 모든 패턴의 기반이 된다.

### 문법

```cpp
int (*fcnPtr)();  // int를 반환하고 매개변수 없는 함수를 가리키는 포인터
```

`*fcnPtr` 둘레의 괄호가 핵심이다 — 괄호 없이 `int* fcnPtr()`라고 쓰면 "int 포인터를 반환하는 함수"로 해석이 완전히 달라진다(연산자 우선순위 문제).

```cpp
int (*const fcnPtr)();  // const 함수 포인터 — const는 * 뒤에 붙는다
```

### 대입과 호출

```cpp
int foo() { return 5; }

int (*fcnPtr)(){ foo };    // 함수 이름은 암묵적으로 함수 포인터로 변환됨
int (*fcnPtr2)(){ &foo };  // &foo로 명시적으로 주소를 써도 동일

fcnPtr();    // 암묵적 역참조 — 관용적으로 이렇게 씀
(*fcnPtr)(); // 명시적 역참조 — 의미는 같음
```

함수 포인터의 타입은 가리키는 함수의 **반환형과 매개변수 목록이 정확히 일치**해야 한다. 시그니처가 다르면 대입 자체가 컴파일 에러다.

### 콜백 — 함수를 인자로 넘기기

함수 포인터의 가장 실용적인 쓰임은 **함수를 다른 함수의 인자로 전달**하는 것이다. 정렬 알고리즘에 오름차순/내림차순 비교 함수를 바꿔 끼우는 예가 대표적이다 — 알고리즘 코드 자체는 손대지 않고 동작을 바꿀 수 있다.

```cpp
using ArithmeticFunction = int (*)(int, int);

int add(int a, int b) { return a + b; }
int subtract(int a, int b) { return a - b; }

int calculate(int x, int y, ArithmeticFunction op)  // 함수를 인자로 받음
{
    return op(x, y);
}

calculate(3, 4, add);       // 7
calculate(3, 4, subtract);  // -1
```

### 함정 — 기본 매개변수는 함수 포인터에서 무시된다

```cpp
void print(int x, int y = 10);
void (*fcnPtr)(int, int){ print };
fcnPtr(1);  // 컴파일 에러! 함수 포인터 호출은 런타임에 결정되므로
            // 컴파일 타임에 채워지는 기본값을 적용할 수 없다
```

기본 매개변수는 컴파일 타임에 호출 지점에서 채워 넣는 문법 설탕인데, 함수 포인터를 통한 호출은 어떤 함수가 불릴지 런타임까지 확정되지 않으므로 이 메커니즘이 작동하지 않는다.

### 실전 표기 — 타입 별칭과 std::function

원시 함수 포인터 문법은 읽기 어렵다. 타입 별칭이나 `std::function`(`<functional>`)으로 가독성을 높인다.

```cpp
using ArithmeticFunction = std::function<int(int, int)>;  // 반환형(매개변수들)
auto fcnPtr{ &foo };  // auto로 타입 추론도 가능
```

> [!WARNING]
> **흔한 실수**
> - `fcnPtr = goo()`처럼 괄호를 붙이면 goo를 **호출한 반환값**을 대입하는 것이지, goo의 주소를 대입하는 게 아니다.
> - `std::cout << foo;`처럼 함수 이름을 그냥 출력하면, 주소가 아니라 암묵적으로 bool로 변환되어 `1`이 찍힌다.
> - 호출 전 null 체크를 하지 않으면 정의되지 않은 동작이 발생할 수 있다.

> rclcpp에서 `std::bind(&MyNode::callback, this, _1)`이나 콜백을 받는 `create_subscription(topic, qos, callback)`이 내부적으로 함수 포인터/`std::function`을 저장하는 구조다. `create_timer`, `create_subscription`이 콜백 타입으로 `std::function`을 요구하는 이유도 여기서 나온다 — 함수 포인터로는 캡처가 있는 람다(다음 [7절](#7-람다-캡처))를 담을 수 없기 때문이다.

## 2. 스택과 힙

### 두 메모리 영역

| 영역 | 관리 방식 | 특징 |
|---|---|---|
| 스택(stack) | 자동 — 함수 진입/종료에 맞춰 자동 할당·해제 | 빠름, 크기 제한 있음(보통 1~8MB) |
| 힙(heap) | 수동 — `new`/`delete`로 직접 관리 | 느림, 훨씬 큼, 명시적 해제 필요 |

```cpp
int x{ 5 };           // 스택에 할당 — 함수 끝나면 자동 소멸
int* ptr{ new int };  // 힙에 할당 — delete ptr; 안 하면 계속 남음
delete ptr;
```

### 왜 스택은 빠르고 힙은 느린가

스택은 **LIFO(후입선출)** 구조로, 함수를 호출할 때마다 "스택 프레임"을 그냥 위로 쌓고 함수가 끝나면 그 프레임을 통째로 걷어낸다 — 포인터 하나 이동시키는 수준의 비용이다. 반면 힙은 "이 크기만큼 빈 블록이 어디 있는지"를 운영체제/런타임이 탐색해서 찾아야 하므로 본질적으로 더 느리다.

### 스택 오버플로우가 발생하는 이유

> "스택의 모든 메모리가 이미 할당된 상태에서 추가 할당이 일어나면, 그 할당은 다른 메모리 영역으로 흘러넘친다."

원인은 크게 두 가지다.
- 스택에 너무 큰 배열을 통째로 선언
- 재귀 호출이 종료 조건 없이(혹은 너무 깊이) 반복되어 스택 프레임이 계속 쌓임 → [3절](#3-재귀)에서 재귀의 종료 조건이 왜 필수인지 이 문제와 직결된다.

### 실무 기준

- 작고 크기가 고정된 지역 변수 → 스택
- 크거나 크기가 실행 중에 정해지는 데이터, 함수 스코프보다 오래 살아야 하는 데이터 → 힙
- 힙 메모리는 반드시 해제 — 안 하면 메모리 누수(leak)

> ROS2에서 `rclcpp::Node::SharedPtr`, `msg->data`처럼 힙에 할당된 객체를 스마트 포인터로 감싸 쓰는 이유가 바로 이 "수동 해제 부담"을 없애기 위해서다. 자세한 자동 해제 메커니즘은 [Ch.22 unique_ptr](../chapter22MoveSemanticsAndSmartPointers/main.md)에서 다룬다.

## 3. 재귀

### 종료 조건이 없으면 안 되는 이유

재귀 함수는 자기 자신을 호출하는 함수다. 매 호출마다 [스택](#2-스택과-힙)에 새 프레임이 쌓이므로, 멈추는 조건(base case)이 없으면 스택이 끝없이 쌓이다가 결국 스택 오버플로우로 프로그램이 죽는다.

```cpp
void countDown(int count)
{
    std::cout << count << '\n';
    if (count > 1)          // 종료 조건 — 이게 없으면 무한 재귀
        countDown(count - 1);
}
```

### 예제 — 팩토리얼

```cpp
int factorial(int n)
{
    if (n <= 1) return 1;              // base case
    return n * factorial(n - 1);       // n을 (n-1)의 팩토리얼에 곱함
}
```

### 예제 — 피보나치와 중복 계산 문제

```cpp
// F(n) = 0 (n=0), 1 (n=1), F(n-1)+F(n-2) (n>1)
int fib(int n)
{
    if (n <= 1) return n;
    return fib(n - 1) + fib(n - 2);
}
```

이 순진한 구현은 `fib(13)` 하나를 구하는 데 함수 호출이 **1,205번** 일어난다 — 같은 하위 문제(`fib(5)` 등)를 계속 다시 계산하기 때문이다.

### 메모이제이션(memoization) — 계산 결과 캐싱

이미 계산한 값을 저장해두고 재사용하면 호출 횟수가 1,205번에서 **35번**으로 급감한다. "같은 입력에 대한 재귀 결과는 항상 같다"는 성질을 활용하는 최적화다.

### 재귀 vs 반복문

| 기준 | 재귀 | 반복문 |
|---|---|---|
| 성능 | 스택 프레임 관리 오버헤드 있음 | 거의 항상 더 빠름 |
| 가독성 | 복잡한 문제(트리 순회 등)를 간결하게 표현 | 로직에 따라 명시적 상태 관리 필요 |
| 안전성 | 깊이가 크면 스택 오버플로우 위험 | 스택 깊이 걱정 없음 |

> "일반적으로 반복문을 선호하되, 재귀가 정말 더 나은 경우에만 재귀를 쓴다" — 코드가 훨씬 단순해지거나, 재귀 깊이가 제한적이거나, 수동 스택 관리를 피하는 이득이 성능 손실을 상쇄할 때다.

## 4. 커맨드 라인 인자

### argc / argv

프로그램을 실행할 때 운영체제가 넘겨주는 문자열 인자들이다. `main()`의 시그니처를 아래처럼 바꾸면 접근할 수 있다.

```cpp
int main(int argc, char* argv[])
```

- **argc** (argument count) — 인자 개수. 프로그램 경로 자신도 포함되므로 최솟값은 1.
- **argv** (argument values) — 각 인자를 가리키는 C 스타일 문자열 배열. 길이는 argc와 같다.

```cpp
int main(int argc, char* argv[])
{
    std::cout << "인자 개수: " << argc << '\n';
    for (int i{ 0 }; i < argc; ++i)
        std::cout << i << ' ' << argv[i] << '\n';
}
```

`MyArgs file.txt 100`으로 실행하면 `argv[0]`은 프로그램 경로, `argv[1]`은 `"file.txt"`, `argv[2]`는 `"100"`이다.

### 문자열 → 숫자 변환

인자는 전부 문자열로 들어오므로, 숫자로 쓰려면 직접 변환해야 한다.

```cpp
std::stringstream convert{ argv[1] };
int myint{};
if (!(convert >> myint))
    myint = 0;  // 변환 실패 시 처리
```

### OS의 인자 분리 규칙

- 공백은 인자를 구분한다 — `MyArgs Hello world`는 인자 2개
- 큰따옴표는 공백을 포함한 하나의 인자로 묶는다 — `MyArgs "Hello world"`는 인자 1개
- 백슬래시는 특수문자를 이스케이프한다

### 왜 쓰는가

배치 처리(여러 파일을 한 번에), 다른 프로그램/스크립트에 의한 자동 실행(웹 서버, 셸 스크립트) 등에 쓰인다. 로보틱스 맥락에서는 ROS2 launch 파일이 노드 실행 파일에 파라미터를 넘길 때 이 메커니즘의 확장판(launch argument, `--ros-args -p`)을 쓴다.

## 5. 생략 부호(...)와 피해야 하는 이유

### 문법

가변 인자를 받는 함수를 만들 때 쓴다. 최소 하나의 고정 매개변수가 먼저 와야 하고, `...`은 항상 마지막에 온다. `<cstdarg>`가 필요하다.

```cpp
double average(int count, ...);
```

### 매크로로 인자 순회

- `va_list` — 생략 부호 인자들을 가리키는 타입
- `va_start(list, count)` — 초기화
- `va_arg(list, type)` — 다음 인자를 지정한 타입으로 꺼냄
- `va_end(list)` — 정리

### 왜 위험한가

**타입 체크가 완전히 꺼진다.** 일반 매개변수는 컴파일러가 인자 타입과 매개변수 타입이 맞는지 검사해주지만, 생략 부호 매개변수에는 타입 선언 자체가 없어서 컴파일러가 검사를 포기한다. `int`가 필요한 자리에 `double`을 넘기면 경고 없이 쓰레기 값이 나온다.

**인자 개수도 알 수 없다.** `...`은 몇 개가 넘어왔는지 정보를 버리므로, 개수를 명시적 매개변수로 넘기거나, 특정 종료값(sentinel)을 두거나, 타입을 설명하는 디코더 문자열을 넘기는 식으로 개발자가 직접 추적해야 한다 — 세 방법 모두 실수하기 쉽다.

### 권장 대안

- 동적 크기 배열(`std::vector` 등)을 넘기기
- 파라미터 팩과 가변 인자 템플릿(C++11+)
- 폴드 표현식(C++17+)

이 대안들은 타입 안전성을 유지하면서 가변 인자를 처리한다 — 그래서 이 챕터 자체가 "웬만하면 `...`을 쓰지 말라"고 명시한다.

## 6. 람다 입문

### 람다란

**람다 표현식(클로저)은 다른 함수 안에 정의된 이름 없는 함수**다. 한 번만 쓰고 버릴 사소한 함수를 위해 굳이 전역 네임스페이스에 이름을 붙여 정의할 필요가 없게 해준다.

### 문법

```
[captureClause] (parameters) -> returnType { statements; }
```

- 캡처절: 캡처할 게 없으면 비워둠 `[]`
- 매개변수: 없으면 생략 가능
- 반환형: 생략하면 `auto`로 추론
- 최소 형태: `[] {}`

### 왜 쓰는가

이전에는 `std::find_if`에 조건을 넘기려면 `containsNut()`처럼 이름 붙은 함수를 따로 정의해야 했다. 람다는 그 로직을 **쓰이는 자리에 바로** 적을 수 있게 해서, 코드를 읽을 때 "무엇을 찾는지"와 "어떻게 찾는지"가 붙어 있게 한다.

```cpp
auto found{ std::find_if(arr.begin(), arr.end(),
    [](std::string_view s) { return s.find("nut") != std::string_view::npos; }) };
```

### 저장할 때는 auto

람다를 변수에 담을 때는 **`auto`를 써야 한다** — 컴파일러가 람다마다 고유한 이름 없는 타입을 만들어내므로, 그 타입을 우리가 직접 쓸 방법이 없다.

함수에 람다를 넘길 때의 선택지:

| 방법 | 특징 |
|---|---|
| `std::function` 매개변수 | 캡처 있는 람다도 저장 가능, 약간의 오버헤드 |
| 함수 템플릿(타입 매개변수) | 오버헤드 없음, 헤더에 구현 노출 |
| C++20 축약 문법(`auto` 매개변수) | 함수 템플릿의 간편 표기 |
| 함수 포인터 | 캡처가 없는 람다에만 가능 |

### 제네릭 람다

C++14부터 매개변수에 `auto`를 쓸 수 있다 — 호출 시점의 실제 타입을 추론하는 "제네릭 람다"가 된다.

> [!NOTE]
> **사용 원칙**
> 람다는 **사소하고 일회성인** 함수에 쓴다. 재사용되거나 복잡한 로직은 이름 있는 일반 함수로 두는 편이 낫다. rclcpp에서 구독자·타이머 콜백을 등록할 때 `[this](const auto& msg) { ... }`처럼 람다를 바로 넘기는 패턴이 여기 해당한다 — 콜백 로직이 짧고 그 노드에서만 쓰인다면 굳이 별도 멤버 함수로 뺄 필요가 없다.

## 7. 람다 캡처

### 캡처가 필요한 이유

캡처절이 없으면 람다 내부에서는 **정적 저장 기간 변수와 constexpr 객체만** 접근할 수 있다. 바깥 스코프의 일반 지역 변수를 쓰려면 캡처로 명시적으로 끌어와야 한다.

### 값으로 캡처

```cpp
int ammo{ 10 };
auto shoot{ [ammo]() { std::cout << ammo; } };
```

- 람다 생성 시점의 값으로 **복사본**을 만든다. 이후 원본이 바뀌어도 람다 안의 복사본은 그대로다.
- 캡처된 변수는 기본적으로 **const** 취급된다 — 수정하려면 `mutable`이 필요하다.

```cpp
int ammo{ 10 };
auto shoot{ [ammo]() mutable { --ammo; } };
shoot();
std::cout << ammo;  // 여전히 10 — 람다 안의 복사본만 줄어듦
```

### 참조로 캡처

```cpp
int ammo{ 10 };
auto shoot{ [&ammo]() { --ammo; } };
shoot();
std::cout << ammo;  // 9 — 원본이 바뀜
```

참조로 캡처하면 non-const 취급이라 `mutable` 없이도 수정할 수 있다(원본 자체가 const가 아닌 한).

### 기본 캡처

- `[=]` — 쓰이는 변수를 전부 값으로 캡처
- `[&]` — 쓰이는 변수를 전부 참조로 캡처
- `[=, &enemies]`, `[&, armor]`처럼 기본 캡처와 개별 캡처를 섞을 수 있다(기본 캡처가 항상 먼저, 같은 변수를 두 번 캡처할 수 없음)

### 캡처절 안에서 변수 새로 만들기

```cpp
auto found{ std::find_if(areas.begin(), areas.end(),
    [userArea{ width * height }](int knownArea) { return userArea == knownArea; }) };
```

`userArea`는 람다 정의 시점에 **한 번만** 계산되어 이후 호출 전체에서 유지된다.

### 위험 — 댕글링 참조

```cpp
auto makeWalrus(const std::string& name)
{
    return [&]() { std::cout << name; };  // 정의되지 않은 동작!
}
```

`name`을 참조로 캡처했는데, `makeWalrus`가 끝나면 그 참조 대상(임시 문자열)이 이미 소멸된 뒤다 — 반환된 람다를 나중에 호출하면 이미 사라진 메모리를 참조한다. **참조로 캡처한 변수는 반드시 람다보다 오래 살아있어야 한다.**

### 위험 — 의도치 않은 복사

```cpp
auto count{ [i]() mutable { std::cout << ++i; } };
auto otherCount{ count };  // count를 복사 — i도 별도로 복사됨
```

`mutable` 람다를 복사하면 캡처된 상태(`i`)까지 통째로 복제되어 서로 독립적으로 움직인다. 이를 막으려면 `std::function`으로 감싸거나 `std::ref()`로 참조를 명시한다.

> [!WARNING]
> **실무 원칙**
> - 기본 타입이 아닌 값은 참조로 캡처하는 편이 효율적이다.
> - `mutable` 람다는 상태를 갖게 되어 실수하기 쉬우니 되도록 피한다.
> - 참조 캡처를 쓸 때는 그 참조 대상이 람다보다 오래 사는지 항상 확인한다 — rclcpp 콜백에서 `[this]`로 노드 포인터를 캡처하는 게 안전한 이유는, 노드 객체가 콜백보다 먼저 파괴될 일이 없도록 스마트 포인터([Ch.22](../chapter22MoveSemanticsAndSmartPointers/main.md))로 수명을 관리하기 때문이다.

| 기본 매개변수 함정 | 함수 포인터 호출에는 기본 매개변수가 적용되지 않음(런타임 결정이라) |

| 힙 | 수동 관리(`new`/`delete`), 느림, 크고 유연함 |
| 재귀 | 자기 자신을 호출. 종료 조건 필수, 메모이제이션으로 중복 계산 제거 |
| 커맨드 라인 인자 | `argc`/`argv`로 실행 시 외부 입력 전달받음 |
| 생략 부호(...) | 타입 체크 완전히 꺼짐 — 웬만하면 템플릿/벡터로 대체 |
| 람다 | 이름 없는 일회성 함수, `auto`로 저장, 캡처절로 바깥 변수 접근 |
| 캡처 | 값(복사, 기본 const) vs 참조(원본 공유, 댕글링 위험) |

### 자주 하는 실수 TOP 5

1. **함수 포인터 선언에서 괄호 빠뜨리기** — `int* fcnPtr()`는 "함수 포인터"가 아니라 "포인터를 반환하는 함수"로 해석된다.
2. **함수 포인터 호출에 기본 매개변수를 기대하기** — 컴파일 에러가 난다.
3. **재귀에 종료 조건을 빠뜨리거나 잘못 두기** — 스택 오버플로우로 프로그램이 죽는다.
4. **생략 부호 인자에 잘못된 타입을 넘기기** — 컴파일러가 경고 없이 통과시키고 런타임에 쓰레기 값이 나온다.
5. **람다에서 참조로 캡처한 지역 변수가 람다보다 먼저 소멸** — 댕글링 참조로 정의되지 않은 동작이 발생한다.
