## 1. 스마트 포인터와 이동 시맨틱 입문

### 원시 포인터의 근본 문제

```cpp
Resource* ptr{ new Resource };
// ... 조기 return이나 예외가 발생하면?
delete ptr;  // 여기까지 도달 못 하면 리소스 누수
```

`delete`를 깜빡 잊는 것도 문제지만, 설령 함수 끝에 `delete ptr;`을 써놨더라도 함수가 도중에 `return`하거나 예외를 던지면 그 줄까지 실행이 도달하지 못한다 — 리소스를 해제할 방법이 원시 포인터 자체에는 없다.

### 스마트 포인터 — 소멸자에 정리를 맡긴다

**스마트 포인터는 동적 할당 메모리를 관리하는 컴포지션 클래스**다. [Ch.15 소멸자](../chapter15MoreOnClasses/main.md)에서 본 RAII 패턴을 그대로 응용한 것 — 스마트 포인터 객체 자체는 스택에 있으므로, 스코프를 벗어나는 순간(조기 return이든 예외든 상관없이) 소멸자가 자동으로 호출되어 안에 담긴 리소스를 해제한다.

### std::auto_ptr — 실패한 첫 시도

C++98이 내놓은 최초의 표준 스마트 포인터 `std::auto_ptr`은 설계 결함 때문에 C++11에서 deprecated, C++17에서 완전히 제거됐다.

- **암묵적 소유권 이전**: 값으로 전달하기만 해도 소유권이 넘어가버려서, 호출자 쪽 포인터가 모르는 사이에 댕글링 상태가 됐다.
- **배열 미지원**: 항상 비배열용 `delete`를 쓰기 때문에 동적 배열을 잘못 해제했다.
- **표준 라이브러리와 충돌**: 컨테이너·알고리즘이 기대하는 "진짜 복사" 의미와 어긋났다.

근본 원인은 **복사 연산자를 이동 연산에 억지로 끼워 맞췄다**는 것이다. `res1 = res2;`를 쓸 때 res2가 여전히 유효한지 아닌지가 코드만 봐서는 불명확했다.

### 복사 vs 이동

| 시맨틱 | 동작 |
|---|---|
| 복사(copy) | 리소스를 통째로 복제 |
| 이동(move) | 리소스의 **소유권만 옮기고** 원본은 비움 |

임시 객체(rvalue)에서 값을 가져올 때는 굳이 비싼 복사를 할 필요가 없다 — 어차피 곧 사라질 객체이므로 "훔쳐 오면" 된다. 이게 이동 시맨틱의 핵심 아이디어다. C++11은 이 개념을 언어 차원에서 정식화해서 `std::unique_ptr`, `std::shared_ptr`, `std::weak_ptr` 세 가지 이동 인식 스마트 포인터를 도입했다.

## 2. r-value 참조

### lvalue와 rvalue

| 구분 | 정의 | 예 |
|---|---|---|
| lvalue | 식별 가능한 객체를 가리키는, 안정적인 주소를 가진 표현식 | 변수 |
| rvalue | 영속적인 위치가 없는 임시 표현식 | 리터럴, 함수의 반환값 |

### 문법

```cpp
int&& rref{ 5 };  // r-value 참조 — && 이중 앰퍼샌드
```

일반 lvalue 참조는 `&` 하나, rvalue 참조는 `&&` 둘이다.

### 왜 필요한가

두 가지 이점이 있다.

1. **수명 연장** — r-value 참조는 자신이 초기화된 임시 객체의 수명을 자기 자신의 수명까지 늘려준다. 원래는 문장이 끝나면 사라질 임시 객체가, r-value 참조에 묶이는 순간 그 참조가 살아있는 동안 계속 유지된다.
2. **수정 가능성** — const가 아닌 r-value 참조를 쓰면 임시 객체를 수정할 수 있다. 이게 이동 시맨틱을 구현할 수 있게 해주는 핵심 통로다 — 임시 객체의 내부 자원을 "훔쳐서" 다른 곳으로 옮길 수 있으려면 그 임시 객체를 수정(내부 포인터를 null로)할 수 있어야 하기 때문이다.

### 바인딩 규칙

| 참조 종류 | lvalue에 바인딩 | rvalue에 바인딩 |
|---|---|---|
| non-const lvalue 참조 | O | X |
| const lvalue 참조 | O | O |
| rvalue 참조 | X | O |

### 반직관적 함정 — 이름 붙은 r-value 참조는 그 자체로 lvalue다

```cpp
void fun(int& lref);   // lvalue 버전
void fun(int&& rref);  // rvalue 버전

int&& ref{ 5 };
fun(ref);  // lvalue 버전이 호출된다! rvalue 버전이 아니라
```

`ref`는 rvalue 참조 **타입**이지만, 일단 이름이 붙어서 변수가 된 이상 표현식 안에서는 **lvalue처럼** 취급된다. "타입이 rvalue 참조"인 것과 "그 변수를 쓰는 표현식이 rvalue인지"는 별개 질문이라는 뜻이다 — 이 구분이 다음 절 이동 생성자에서 함수 매개변수(`other`)를 왜 `std::move`로 다시 감싸야 하는지의 근거가 된다.

### 실전 용도

r-value 참조는 대부분 **함수 오버로딩의 매개변수**로 쓰여서, "임시 객체가 넘어왔는지 아닌지"에 따라 다른 동작(복사 vs 이동)을 고르게 해준다 — [다음 절](#3-이동-생성자와-이동-대입)에서 바로 이 패턴을 본다.

## 3. 이동 생성자와 이동 대입

### 왜 필요한가

리소스를 소유한 클래스(예: 동적 메모리를 담은 스마트 포인터류)를 복사할 때, 복사 생성자는 항상 깊은 복사(deep copy)를 한다 — 비용이 크다. 그런데 인자로 넘어온 게 어차피 곧 사라질 **임시 객체(r-value)**라면, 굳이 복사할 필요 없이 **자원 소유권만 옮기면** 된다. 이게 훨씬 싸다.

> "생성자나 대입 연산의 인자가 r-value라면, 그건 어떤 종류든 임시 객체라는 뜻이다. 그걸 복사하는(비용이 큰) 대신, 그냥 리소스를 옮기면(비용이 적게 든다) 된다."

### 복사와 이동의 차이

| 구분 | 복사 | 이동 |
|---|---|---|
| 매개변수 | `const T&` (lvalue 참조) | `T&&` (rvalue 참조) |
| 동작 | 리소스를 깊은 복사 | 소유권 이전 |
| 한정자 | 특별한 요구 없음 | `noexcept` 표시 권장 |
| 결과 | 원본 그대로 유지 | 원본은 "유효하지만 정해지지 않은" 상태로 남음 |

### 문법

```cpp
class ClassName
{
public:
    ClassName(ClassName&& other) noexcept
        : m_ptr{ other.m_ptr }
    {
        other.m_ptr = nullptr;  // 원본 포인터를 비워둔다
    }

    ClassName& operator=(ClassName&& other) noexcept
    {
        if (&other == this) return *this;
        delete m_ptr;
        m_ptr = other.m_ptr;
        other.m_ptr = nullptr;  // 여기도 반드시 비워야 한다
        return *this;
    }
};
```

**원본 포인터를 반드시 null로 비워야 하는 이유**는, 안 비우면 원본과 새 객체가 같은 메모리를 가리킨 채로 각자의 소멸자에서 `delete`를 호출하게 되어 이중 해제(double free)가 발생하기 때문이다.

### 실측 효과

`Auto_ptr` 예제에서, 리소스를 관리하는 객체를 반환하는 단순한 함수 하나가 복사 시맨틱만 있을 때는 `Resource` 객체를 세 번 만들고 세 번 없앴다(오버헤드 큼). 이동 시맨틱을 구현하면 생성 1번, 소멸 1번으로 줄어든다. 100만 개 정수를 다루는 `DynamicArray` 벤치마크에서는 이동 시맨틱 적용 시 **32.1% 더 빨랐다**.

### 컴파일러가 암묵적으로 만들어주는 조건

아래 세 가지가 모두 없을 때만 컴파일러가 암묵적 이동 생성자/대입을 만들어준다.
- 사용자가 정의한 복사 생성자/대입이 없음
- 사용자가 정의한 이동 생성자/대입이 없음
- 사용자가 정의한 소멸자가 없음

> [!WARNING]
> **암묵적 이동의 함정**
> "암묵적 이동 생성자와 이동 대입은 포인터를 **이동시키지 않고 복사**한다." 즉 리소스를 소유하는 클래스가 소멸자를 직접 정의해둔 순간, 컴파일러는 이동 연산 생성을 포기하고 복사로 대체 — 명시적으로 이동 생성자/대입을 작성하지 않으면 여전히 복사 시맨틱으로 동작한다.

### Rule of Five

특수 멤버 함수 다섯 가지 — 복사 생성자, 복사 대입, 이동 생성자, 이동 대입, 소멸자 — 는 하나라도 직접 정의하거나 삭제(`= delete`)하면 나머지 넷도 의도를 명시적으로 밝혀야 한다는 원칙이다. 그래야 "일부는 예상대로 동작하고 일부는 암묵적으로 다르게 동작하는" 미묘한 버그를 막을 수 있다.

- **이동 전용 클래스**: 복사는 삭제하고 이동만 남긴다 — `std::unique_ptr`이 이 패턴이다([5절](#5-stdunique_ptr)).
- **명시적 기본값**: `= default`로 "컴파일러가 만든 버전을 의도적으로 그대로 쓰겠다"는 걸 명시한다.

> [!WARNING]
> **이동 구현에서 std::swap을 쓰지 말 것**
> 이동 가능한 멤버에 대해 이동 구현 안에서 `std::swap()`을 쓰면 무한 재귀에 빠진다. 대신 멤버 단위로 직접 동작하는 커스텀 swap 함수를 만든다.

## 4. std::move

### 무엇을 하는가

`std::move`(`<utility>`)는 **lvalue를 rvalue 참조로 캐스팅**하는 함수다 — 내부적으로 `static_cast`를 쓴다. 값 자체는 아무것도 옮기지 않고, "이 lvalue를 이동 시맨틱 대상으로 취급해도 된다"는 컴파일러용 표시만 붙이는 것이다.

### 왜 필요한가

이동 생성자/대입은 `T&&`(r-value 참조)를 매개변수로 받는데, 우리가 이동시키고 싶은 대상이 **이름 붙은 변수(lvalue)**인 경우가 많다. [2절](#2-r-value-참조)에서 봤듯 이름 붙은 변수는 그 자체로 lvalue라서, 아무 표시 없이 넘기면 컴파일러가 복사 버전을 고른다. `std::move`는 이 lvalue를 강제로 rvalue처럼 보이게 만들어서 이동 버전이 선택되게 한다.

```cpp
template <typename T>
void mySwap(T& a, T& b)
{
    T tmp{ std::move(a) };  // 이동 생성자 호출
    a = std::move(b);       // 이동 대입 호출
    b = std::move(tmp);     // 이동 대입 호출
}
```

`a`, `b`는 매개변수로서 lvalue 참조이므로, `std::move` 없이는 이동 생성자/대입을 호출할 방법이 없다 — 세 번의 값 복사 대신 세 번의 소유권 이동으로 바뀐다.

```cpp
std::string str{ "안녕" };
std::vector<std::string> v{};
v.push_back(std::move(str));  // str의 내용을 "훔쳐서" 벡터에 넣음 — 복사 안 함
```

### 언제 쓰는가

- 값 교환(swap)
- lvalue로 컨테이너 채우기
- 요소 교환이 일어나는 정렬 알고리즘
- 스마트 포인터 간 소유권 이전

### 함정 — 이동된 뒤(moved-from) 객체 사용

`std::move`를 적용한 뒤 원본 객체는 **"유효하지만 내용이 정해지지 않은" 상태**가 된다.

| 안전한 연산 | 위험한 연산 |
|---|---|
| `operator=`로 재대입 | `operator[]` |
| `clear()`, `reset()` | `front()` |
| `empty()` 같은 상태 확인 | 유효한 데이터가 있다고 가정하는 모든 연산 |

**원칙**: 이동 이후 값을 다시 쓸 필요가 없을 때만 `std::move`를 쓰거나, 쓰더라도 곧바로 재대입할 계획일 때만 쓴다.

## 5. std::unique_ptr

### 목적과 소유권 모델

`std::unique_ptr`는 **여러 객체가 공유하지 않는** 동적 할당 객체를 관리하기 위한 스마트 포인터다. 스코프를 벗어나면 자동으로 관리 대상을 delete하므로, 수동 메모리 관리와 조기 return/예외로 인한 누수 문제를 원천적으로 없앤다.

### 배타적 소유권 — 복사가 막혀 있는 이유

`std::unique_ptr`는 **한 순간에 오직 하나의 unique_ptr만** 리소스를 소유하도록 강제한다. 그래서 복사 생성/복사 대입이 명시적으로 비활성화되어 있다 — `std::auto_ptr`가 저질렀던 "암묵적 소유권 이전 + 이중 해제" 문제를 원천 차단하는 설계다.

```cpp
std::unique_ptr<Resource> res1{ new Resource };
std::unique_ptr<Resource> res2{ res1 };  // 컴파일 에러 — 복사 금지
```

소유권을 옮기려면 반드시 [std::move](#4-stdmove)를 거쳐야 한다.

```cpp
std::unique_ptr<Resource> res2{ std::move(res1) };  // res1은 이제 null, res2가 소유
```

### std::make_unique를 써야 하는 이유

```cpp
auto res{ std::make_unique<Resource>() };
```

- 코드가 간결해진다.
- **예외 안전성** — `new Resource`를 직접 써서 스마트 포인터 생성자에 넘기는 방식은, 인자 평가 순서에 따라 스마트 포인터가 만들어지기 전에 예외가 나서 리소스가 누수될 여지가 있다. `make_unique`는 이 문제를 원천 차단한다.

### 배열 관리는 대안을 우선 고려

`std::unique_ptr`는 스칼라/배열 삭제를 자동으로 구분하긴 하지만, "`std::array`, `std::vector`, `std::string`이 거의 항상 더 나은 선택"이다.

### 함수에 넘길 때

| 방식 | 의미 | 언제 |
|---|---|---|
| 값으로 전달 + `std::move` | 소유권 이전 — 함수가 리소스 책임을 완전히 넘겨받음 | 함수가 그 리소스를 계속 소유해야 할 때 |
| `.get()`으로 원시 포인터 추출 | 소유권은 그대로, 잠깐 빌려줌 | 함수가 그냥 값만 쓰고 끝날 때(선호되는 방식) |

`.get()` 방식이 선호되는 이유는 "함수가 호출자가 리소스를 어떻게 관리하는지 알 필요가 없게" 만들기 때문이다.

### 함정

- 같은 리소스를 여러 `unique_ptr`가 관리하게 두면(복사를 억지로 우회하거나 원시 포인터로 각각 생성) 이중 해제가 발생한다.
- `unique_ptr`가 아직 소유 중인 리소스를 수동으로 `delete`하면 안 된다.

`std::make_unique()`를 쓰는 습관 자체가 이 두 실수를 자연스럽게 막아준다.

> ROS2에서 `std::unique_ptr<rclcpp::Node>`처럼 배타적 소유가 명확한 리소스(단일 소유자 노드, 플러그인 인스턴스)에 unique_ptr가 쓰인다 — 반면 여러 콜백/여러 곳에서 공유해야 하는 `rclcpp::Node::SharedPtr`는 다음 절의 shared_ptr다.

## 6. std::shared_ptr

### unique_ptr와의 근본적 차이

`std::unique_ptr`가 배타적 소유라면, `std::shared_ptr`는 **여러 스마트 포인터가 하나의 리소스를 공동으로 소유**하게 해준다. 리소스는 그 리소스를 참조하는 shared_ptr가 **하나라도 남아있는 한** 계속 살아있다.

### 참조 카운팅의 내부 구조

`std::shared_ptr`는 내부에 포인터 두 개를 갖는다.
- 관리 대상 리소스를 가리키는 포인터
- **제어 블록(control block)** — 참조 카운트를 추적하는, 별도로 동적 할당된 구조체를 가리키는 포인터

마지막 shared_ptr가 스코프를 벗어날 때 참조 카운트가 0이 되고, 그때 리소스가 해제된다.

### 함정 — 원시 포인터에서 독립적으로 생성하지 말 것

```cpp
Resource* res{ new Resource };
std::shared_ptr<Resource> ptr1{ res };
std::shared_ptr<Resource> ptr2{ res };  // 위험! 서로 다른 제어 블록을 가짐
```

`ptr1`과 `ptr2`가 **각자 별도의 제어 블록**을 만들어버려서, 둘 다 "내가 마지막"이라고 착각하고 각자 delete를 호출한다 — 이중 해제.

### 안전한 방법 — 기존 shared_ptr를 복사

```cpp
auto ptr2{ ptr1 };  // 안전 — 같은 제어 블록을 공유하며 참조 카운트만 증가
```

### 권장 방법 — std::make_shared

```cpp
auto ptr1{ std::make_shared<Resource>() };
```

리소스 할당과 제어 블록 할당을 **한 번의 메모리 할당**으로 합쳐서 처리하므로 성능과 안전성 모두 유리하다 — `std::make_unique`와 같은 이유다.

### 리소스 수명

중간에 있는 shared_ptr가 스코프를 벗어나는 것만으로는 리소스가 해제되지 않는다 — **마지막 하나**가 파괴되거나 재대입될 때만 해제된다.

### unique_ptr → shared_ptr 변환

`std::unique_ptr`는 이동을 통해 `std::shared_ptr`로 변환할 수 있다. 반대 방향(shared_ptr → unique_ptr)은 안전하지 않아 지원되지 않는다 — 다른 shared_ptr들이 여전히 그 리소스를 참조하고 있을 수 있는데, unique_ptr는 "나 혼자만 소유"를 전제하기 때문이다.

### 한계

- C++20 이전에는 배열을 제대로 지원하지 않는다.
- 관리 중인 모든 포인터가 제대로 파괴돼야 리소스가 해제된다.
- **순환 참조 문제**에 취약하다 → [다음 절](#7-stdshared_ptr의-순환-참조-문제와-stdweak_ptr)

> `rclcpp::Node::SharedPtr`가 바로 이 shared_ptr다 — 여러 콜백, 여러 컴포넌트가 같은 노드 인스턴스를 동시에 참조해야 하므로 배타적 소유(unique_ptr)로는 표현할 수 없고, `std::make_shared<Node>()`로 노드를 생성하는 관용구도 위 make_shared 권장 사항 그대로다.

## 7. std::shared_ptr의 순환 참조 문제와 std::weak_ptr

### 순환 참조가 왜 메모리 누수인가

두 객체가 서로를 `shared_ptr`로 가리키는 상황을 생각해보자 — `lucy`가 `ricky`를 가리키고 `ricky`도 `lucy`를 가리킨다.

- `lucy`가 스코프를 벗어나도, `ricky`가 여전히 `lucy`를 가리키는 shared_ptr를 갖고 있으므로 참조 카운트가 0이 안 되어 해제되지 않는다.
- `ricky`가 스코프를 벗어나도 마찬가지로 `lucy`가 살아있게 만든다.

> "각 객체가 다음 객체를 계속 살려두는 셈이다 — 마지막 객체가 첫 번째 객체를 살려두는 것까지 포함해서."

결과적으로 둘 다 파괴되지 않는다 — 참조 카운팅 방식의 근본적인 약점이다.

### 해결책 — std::weak_ptr

`std::weak_ptr`는 리소스를 **관찰만 하고 소유권에는 참여하지 않는** 포인터다. 핵심 성질:

> "shared_ptr가 스코프를 벗어날 때는 다른 shared_ptr가 공동 소유하고 있는지만 따진다. weak_ptr는 카운트에 들어가지 않는다!"

즉 `Person`끼리의 상호 참조 중 하나를 `std::shared_ptr` 대신 `std::weak_ptr`로 바꾸면, 진짜 소유자(shared_ptr)가 모두 사라졌을 때 정상적으로 해제된다.

### 사용법

`std::weak_ptr`는 `operator->`가 없으므로, 실제로 접근하려면 `lock()`으로 shared_ptr로 변환해야 한다.

```cpp
std::shared_ptr<Person> partner = m_partner.lock();
```

만료 여부는 `expired()`로 미리 확인할 수 있고, 만료된 weak_ptr에 `lock()`을 호출하면 `nullptr`가 반환된다(예외가 아니다).

```cpp
if (!m_partner.expired())
{
    // lock() 호출이 안전함
}
```

> ROS2 노드 그래프에서 부모-자식 관계나 콜백 그룹처럼 "서로를 알아야 하지만 소유 관계는 아닌" 참조에 weak_ptr 패턴이 쓰인다 — `this`를 shared_ptr로 캡처해서 순환을 만들 위험이 있는 콜백 등록 시 `weak_from_this()`를 쓰는 이유가 바로 이 순환 참조 회피다.

## 핵심 요약 카드

| 개념 | 핵심 내용 |
|---|---|
| 스마트 포인터 | 소멸자로 자동 해제하는 리소스 관리 클래스. RAII의 응용 |
| std::auto_ptr | 복사=이동 혼동으로 실패 → C++17에서 제거됨 |
| r-value 참조(`&&`) | 임시 객체에 바인딩, 수명 연장 + 수정 가능 |
| 이동 생성자/대입 | `T&&` 매개변수로 소유권만 이전, 원본은 null로 비움 |
| Rule of Five | 5대 특수 멤버 함수 중 하나 건드리면 전부 명시적으로 다뤄야 함 |
| std::move | lvalue를 rvalue로 캐스팅 — 실제로 아무것도 옮기지 않음 |
| std::unique_ptr | 배타적 소유, 복사 금지, `make_unique` 권장 |
| std::shared_ptr | 참조 카운팅 공동 소유, `make_shared` 권장, 마지막 하나가 없어질 때 해제 |
| std::weak_ptr | 소유권 없는 관찰자, 순환 참조로 인한 누수를 막음 |

### 자주 하는 실수 TOP 5

1. **이동 생성자/대입에서 원본 포인터를 null로 안 비우기** — 이중 해제(double free)로 이어진다.
2. **같은 원시 포인터로 shared_ptr 두 개를 독립적으로 생성** — 제어 블록이 갈라져서 이중 해제가 발생한다. 항상 기존 shared_ptr를 복사하거나 `make_shared`를 쓴다.
3. **이동된(moved-from) 객체를 마치 유효한 데이터가 있는 것처럼 사용** — `operator[]`, `front()` 등은 정의되지 않은 동작을 일으킬 수 있다.
4. **소멸자만 직접 정의하고 이동 생성자/대입은 안 만들기** — 암묵적 이동이 사라지고 조용히 복사로 대체된다.
5. **shared_ptr끼리 순환 참조를 만들고 weak_ptr를 안 씀** — 참조 카운트가 절대 0이 안 되어 메모리가 영원히 해제되지 않는다.
