## 1. 함수 오버로딩 소개 (11.1)

같은 이름의 함수를 **매개변수 목록이 다르게** 여러 개 정의할 수 있다.

```cpp
int add(int a, int b) { return a + b; }
double add(double a, double b) { return a + b; }
```

**왜 필요한가**: `addInt`, `addDouble`처럼 타입마다 함수 이름을 따로 지으면 호출부에서 매번 타입을 신경 써야 한다. 오버로딩은 "무엇을 하는지"는 이름 하나로 통일하고 "어떤 타입에 대해"는 컴파일러가 인자로부터 알아서 고르게 한다.

---

## 2. 오버로드를 구분하는 기준 (11.2)

컴파일러가 오버로드를 구분하는 건 **매개변수 타입/개수**뿐이다. **<mark style="background: #ADCCFFA6;">반환 타입(return)</mark>만 다른 건 오버로드로 인정되지 않는다.**

```cpp
int getValue();
double getValue();   // 컴파일 에러 — 매개변수가 똑같아서 오버로드가 아니라 재정의 충돌
```

값 전달(`int`)과 참조 전달(`int&`)은 서로 다른 오버로드로 취급되지만, `const` 유무만 다른 값 전달(`int` vs `const int`)은 호출자 입장에서 구분이 안 되므로 오버로드로 인정되지 않는다.

```cpp
void print(int x);
void print(int x, int y);        // OK — 매개변수 개수가 다름
void print(int x, double y);     // OK — 두 번째 매개변수 타입이 다름
void print(double x, int y);     // OK — 순서까지 포함해서 타입 목록이 다르면 별개 오버로드
```

**왜 순서까지 따지는가**: 오버로드 구분은 "타입 목록"을 통째로 비교하기 때문에, 같은 타입들이라도 순서가 다르면 컴파일러 입장에선 완전히 다른 시그니처다. `print(int, double)`과 `print(double, int)`는 사람 눈엔 비슷해 보여도 각각 다른 함수로 취급된다.

---

## 3. 오버로드 해석과 모호한 매칭 (11.3)

여러 오버로드 중 하나를 고르는 절차는 **매칭 등급 순서**로 진행된다: ① 정확히 일치 → ② 승격 매칭 → ③ 수치 변환 매칭 → ④ 사용자 정의 변환. 가장 좋은 등급의 후보가 **단 하나**면 그걸 쓰고, 같은 등급 후보가 여러 개면 **ambiguous match 컴파일 에러**다.

```cpp
void f(int);
void f(double);
f(5L);   // long → 둘 다 수치 변환 등급이라 모호할 수 있음 (컴파일러/표준에 따라 에러)
```

**왜 함정인가**: "컴파일러가 알아서 제일 비슷한 걸 고르겠지"라는 기대와 달리, 등급이 같으면 **아예 컴파일이 안 된다** — 조용히 잘못된 쪽을 고르는 게 아니라 명시적으로 실패해서 오히려 안전한 설계다.

---

## 4. 삭제된 함수 — delete (11.4)

특정 오버로드가 **호출되면 안 되는 상황**을 컴파일 타임에 막고 싶을 때 `= delete`를 붙인다.

```cpp
void print(int x);
void print(double) = delete;   // print(3.5) 호출을 의도적으로 막음 — 암시적 변환도 막힘
```

**왜 쓰는가**: 정수 전용 함수에 실수로 부동소수점을 넘기면 조용히 narrowing 변환돼 버그가 될 수 있는데, `delete`로 막아두면 그 호출 자체가 컴파일 에러가 된다 — "이 타입 조합은 애초에 말이 안 된다"를 컴파일러가 강제하게 만드는 장치.

---

## 5. 기본 인자 (11.5)

```cpp
void log(const std::string& msg, int level = 1); // level = 1 -> default 존재
log("start");        // level = 1
log("start", 2);      // level = 2
```

**규칙**: <mark style="background: #ADCCFFA6;">default값이 있는 매개변수는 **없는 매개변수보다 뒤**에만</mark> 올 수 있다. 기본 인자와 오버로딩을 같이 쓰면 호출이 모호해질 수 있어 주의가 필요하다 — 사실상 "인자 개수가 다른 여러 오버로드"를 하나로 압축한 것과 같은 효과를 내기 때문.

## 6. 함수 템플릿 (11.6)

타입만 다르고 **로직이 완전히 같은 함수를 오버로딩으로 여러 벌 손으로 찍어내는 대신**, 타입 자체를 매개변수로 만든다.

```cpp
template <typename T>
T max_(T a, T b)
{
    return (a > b) ? a : b;
}
```

**왜 오버로딩 대신 템플릿인가**: 오버로딩은 타입마다 함수 본문을 사람이 직접 복붙해야 하지만, 템플릿은 본문을 한 번만 쓰고 **컴파일러가 호출 시점에 실제 타입으로 코드를 찍어낸다(인스턴스화)**. 로직이 똑같은데 타입만 다르면 템플릿, 타입마다 로직이 진짜 달라야 하면 오버로딩을 쓴다.

---

## 7. 템플릿 인스턴스화 (11.7)

```cpp
max_(3, 5);       // 컴파일러가 T=int 버전 함수를 이 시점에 생성
max_(3.1, 5.2);    // T=double 버전을 또 생성
```

**왜 알아야 하는가**: <mark style="background: #ADCCFFA6;">템플릿 자체는 코드가 아니라 "코드를 찍어내는 틀"</mark>이라, 실제로 호출된 타입 조합만큼만 함수가 생성된다(코드 크기 증가 요인). 또한 인스턴스화는 **호출 시점에** 일어나므로, 템플릿 정의는 보통 헤더 <mark style="background: #ADCCFFA6;">파일에 통째로 있어야 한다</mark>(컴파일 단위마다 인스턴스화가 필요하기 때문).

> [!NOTE]
> **그럼 .cpp 파일엔 템플릿을 어떻게 쓰나?**
> `.cpp`에는 템플릿 정의를 다시 안 쓰고, 헤더를 `#include`해서 평범한 함수처럼 호출만 한다.
>
> ```cpp
> // MaxUtils.h — 템플릿 정의가 통째로 여기 들어있음
> #ifndef MAXUTILS_H
> #define MAXUTILS_H
>
> template <typename T>
> T max_(T a, T b)
> {
>     return (a > b) ? a : b;
> }
>
> #endif
> ```
>
> ```cpp
> // main.cpp
> #include "MaxUtils.h"
> max_(3, 5);       // T=int로 인스턴스화
> max_(3.1, 5.2);    // T=double로 인스턴스화
> ```
>
> 일반 함수는 정의가 한 번만 컴파일돼 링커가 나중에 연결하지만, 템플릿은 **호출된 타입을 봐야** 실제 코드를 찍어낼 수 있다. 그 타입은 각 `.cpp`(번역 단위) 안에서 정해지므로, 템플릿 정의 자체가 그 번역 단위에 보여야 인스턴스화가 가능하다 — 그래서 정의를 헤더에 두고 include로 끌어온다. 여러 `.cpp`가 같은 타입으로 인스턴스화해도 링커가 중복을 자동으로 합쳐준다.

## 8. 템플릿 타입 여러 개 (11.8)

```cpp
template <typename T, typename U>
auto add(T a, U b)
{
    return a + b;   // 반환 타입은 auto로 추론
}

add(3, 4.5);   // T=int, U=double, 반환은 double
```

**왜 필요한가**: 매개변수 두 개가 서로 다른 타입일 수 있는데 템플릿 매개변수가 하나뿐이면 `max_(3, 4.5)`처럼 타입이 섞인 호출에서 추론이 실패한다. 반환 타입을 손으로 정하기 애매할 때는 `auto`(반환 타입 추론)에 맡기는 게 자연스럽다.
